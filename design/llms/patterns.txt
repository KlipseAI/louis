Patterns는 소비 제품의 화면별 관측값보다 우선하는 신규 작업 규범이다. 제품 통합이 Pattern과 다르면

## Loading

- Source: design/patterns/loading.md

### Loading

로딩 UI는 사용자가 **무엇을 기다리는지, 얼마나 진행됐는지, 실패하면 무엇을 할 수 있는지** 이해하게
해야 한다. 모든 진행 상태를 spinner 하나로 처리하지 않는다.

#### 선택 기준

| 상황                                 | 기본 표현                            | 이유                                           |
| ------------------------------------ | ------------------------------------ | ---------------------------------------------- |
| 버튼·짧은 인라인 액션                | `InlineLoadingLabel`                 | 액션이 시작됐고 중복 입력이 막혔음을 바로 전달 |
| 작은 독립 영역, 완료 시간을 모름     | `LoadingSpinner` + 짧은 문구         | 레이아웃을 예측할 필요가 없음                  |
| 구조가 정해진 카드·목록의 첫 로드    | Skeleton                             | 나타날 콘텐츠 구조를 미리 전달                 |
| 업로드·다운로드·렌더처럼 진행률을 앎 | Determinate progress                 | 남은 정도를 설명할 수 있음                     |
| 장시간 백그라운드 작업               | 지속 상태 + 진행/취소/다른 작업 허용 | 사용자를 화면에 묶어 두지 않음                 |
| 진행률을 **모르는 장시간 생성**       | 생성 중 셸 (아이콘 breathe 루프)      | 미디어 생성처럼 수십 초가 걸리고 자리 모양도 진행률도 모르는 곳 |

시머 텍스트는 기존 목록 화면의 관측 패턴이다. 신규 패턴으로 확장하기 전에 Skeleton 또는 Spinner로
같은 목적을 더 명확히 해결할 수 있는지 먼저 검토한다.

#### 생성 중 셸 — 제품 실측

**미디어 생성은 위 다섯 중 어디에도 안 맞는다.** 수십 초가 걸리는데 진행률을 모르고, 나타날
콘텐츠의 구조도 모른다 — Skeleton도 Determinate도 쓸 수 없다. 제품은 **매체 아이콘 하나를
호흡시키는** 여섯 번째 표현을 쓴다.

| 축 | 값 |
| --- | --- |
| 아이콘 박스 | `64px` |
| 아이콘 색 | 매체별 accent — Image `--accent-green-500`(`ImageNode.tsx:332`) · Video `--primary-500`(`VideoNode.tsx:240`) · Text `--accent-yellow-500`(`TextNode.tsx:321`) · Edit `--accent-violet-500`(`EditNode.tsx:375`) |
| 셸 | `flex column` · 가운데 정렬 · `gap: 4px` · `width/height: 100%` · `min-height: 120px` |
| 셸 기타 | `overflow: hidden` · `pointer-events: none` |
| 캡션 | 아이콘 **다음에 오는 i18n 단계 라벨** — `type-body-14-medium` · 매체 accent(Image 는 다크 `--accent-green-100` / 라이트 `--accent-green-700`, `ImageNode.tsx:351-352`) |
| 시맨틱 | **`role="status"` · `aria-live="polite"`** |

**읽히는 것은 캡션이다.** 셸이 `role="status"`·`aria-live="polite"` 를 갖는데 그 안에서 텍스트를
가진 자식은 캡션 하나뿐이다 — 아이콘은 `aria-hidden` 이다(`ImageNode.tsx:731-749`). 시맨틱만 계약하고
캡션을 계약하지 않으면 **읽어 줄 문장이 없는 live region** 이 된다. Image 셸은 아이콘과 캡션 둘이
전부이고, Edit 셸은 같은 두 자식에 진행 채움과 `role="progressbar"` 가 더 붙는다
(`EditNode.tsx:568-593`).

모션은 **2단이고 이어 붙는다.**

| 단계 | 값 |
| --- | --- |
| 등장 | `media-icon-grow-in 320ms cubic-bezier(0.22, 1, 0.36, 1) both` — `scale(0.8)` + `opacity 0` → `scale(1)` + `opacity 1` |
| 호흡 | `media-icon-breathe 1000ms cubic-bezier(0.34, 1.56, 0.64, 1) 320ms infinite` — `0%·100% scale(1)` / `50% scale(1.14)` |

**딜레이 320ms가 등장 길이와 같고, 호흡의 `0%`가 등장의 종료값과 같다.** 그래서 이어질 때 튀지
않는다. **두 값을 따로 정하면 반드시 튄다.**

`prefers-reduced-motion`에서 `animation: none`이라 **두 단계가 함께 사라지고 `scale(1)`에서
멈춘다.** 아이콘은 그대로 보인다.

##### Motion 계약과 어긋나는 두 가지

**[Motion](../foundations/motion.md)의 loop 계약이 이 표현을 담지 못한다.**

1. 허용 property에 `transform`/`scale`이 없다 — 현재 셋(`opacity` · `rotate` ·
   `background-position`)뿐이다.
2. loop recipe 둘(등속 회전 · standard 시머) 어느 쪽도 **overshoot 곡선**
   (`cubic-bezier(0.34, 1.56, 0.64, 1)`)이 아니다. 이 곡선은 1을 넘었다 돌아온다.

**판정이 필요하다.** loop에 `transform` 축과 overshoot recipe를 추가할지, 이 표현을 제품 전용으로
둘지. 정하지 않으면 화면을 조립할 때마다 곡선을 지어내게 된다.

근거: `nodes/ImageNode.tsx:328-334` · `keyframes.css:410`·`:422`.

#### 시간과 피드백

- 매우 짧은 응답은 불필요한 깜빡임을 만들지 않도록 표시를 지연할 수 있다. 공통 threshold는 P2 motion
  결정 전까지 package에 하드코딩하지 않는다.
- 4초를 넘길 가능성이 있으면 `처리 중` 같은 구체적 상태 문구를 함께 제공한다.
- 10초 이상이면 현재 단계, 실패 가능성, 재시도 또는 취소 방법을 제공한다.
- 1분 이상이면 백그라운드 처리와 화면 이탈 후 재확인 경로를 우선 검토한다.

#### 생명주기

1. **Start** — 입력을 수락하고 중복 실행을 차단한다. 해당 컨트롤에 `aria-busy`를 제공한다.
2. **Progress** — 작업 대상과 상태를 유지한다. 진행률을 알면 determinate UI를 쓴다.
3. **Success** — 결과가 화면 자체로 분명하면 별도 성공 Toast를 중복해서 띄우지 않는다.
4. **Failure** — 원인, 영향, 다음 행동을 해당 영역 가까이에 제공한다. 재시도 가능 여부를 명시한다.
5. **Cancel** — 취소가 가능한 긴 작업은 진행 상태 안에서 직접 취소할 수 있게 한다.

#### 문구

- `생성 중`, `업로드 중`, `Analyzing`처럼 상태를 구체적으로 쓴다.
- 진행 문구 끝의 `...`/`…`는 사용하지 않는다.
- `Loading` 같은 범용 접근성 라벨 대신 화면의 i18n 문구를 제공한다.
- 실패 문구는 `오류가 발생했습니다`로 끝내지 않고 사용자가 할 수 있는 다음 행동을 포함한다.

#### Accessibility

- 독립 Spinner는 `role="status"`, `aria-live="polite"`, `aria-busy="true"`와 문맥별 이름을 가진다.
- 인접 텍스트가 상태를 설명하면 Spinner는 `decorative`로 두고 부모가 접근 가능한 이름을 소유한다.
- Skeleton은 장식으로 숨기고, 실제 로딩 영역이 `aria-busy`를 소유한다.
- `prefers-reduced-motion: reduce`에서는 회전·shimmer를 정적 상태로 바꾸되 로딩 의미는 텍스트로
  유지한다.
- 로딩 중 기존 콘텐츠를 제거해 포커스가 예기치 않게 사라지지 않게 한다.

#### Implementation status

Web과 Figma 구현은 아직 `not-ready`다. 기존 제품의 spinner, inline loading, skeleton/shimmer 근거는
[`KP-LOADING-001`](../../migration/product-baseline.md)에 비규범 기준선으로 보존한다.

#### Pre-implementation blockers

- 공용 Spinner, Skeleton과 Button loading API가 없다.
- live region과 `aria-busy` 조합 test가 없다.
- reduced-motion recipe와 progress semantics가 package로 배포되지 않는다.
- Figma loading state 가 template 축으로 대조되지 않는다 — 패턴의 대조 상대인
  `figma/templates.measured.json` 은 고정 커밋의 제품 실측이라 「지금 코드가 그 값을 만든다」가
  서지 않는다. **게시 여부는 이 결손과 무관하다**
  ([DS-D-0035](../governance/decisions/DS-D-0035-figma-done-without-publish.md)).

#### Acceptance tests

- 승인된 delay threshold 안의 짧은 작업에서 불필요한 flash가 없고, 지연 후에는 무엇을 기다리는지
  이름이 보인다.
- loading 중 중복 activation이 차단되며 기존 focus가 제거되지 않는다.
- indeterminate와 determinate 상태가 screen reader에 중복 없이 전달된다.
- 실패 시 loading UI가 사라지고 오류, retry 또는 cancel 경로가 제공된다.
- Skeleton은 접근성 트리에서 숨고 실제 영역이 `aria-busy`를 소유한다.
- reduced-motion에서 회전·shimmer를 제거해도 텍스트로 상태를 이해할 수 있다.
- 200% zoom과 KO/EN/JA 긴 문구에서 상태와 핵심 action이 잘리지 않는다.

**새 CSS가 없다.** 이 패턴은 컴포넌트가 아니라 **경계**다 — 무엇을 언제 쓰는가와 누가 로딩을
알리는가를 정한다. 부품은 [Spinner](../components/spinner.md)와

##### 무엇을 쓰는가

| 자리 | 쓰는 것 | 왜 |
| --- | --- | --- |
| 올 내용의 **모양을 아는** 곳 | Skeleton | 목록 행·카드 격자·프로필 머리. 도착했을 때 화면이 튀지 않는다 |
| 모양을 **모르는** 곳 | Spinner | 버튼 안, 짧은 동작. 틀린 자리표시는 없는 것보다 나쁘다 |
| 진행률을 **아는** 곳 | 아직 없다 | determinate progress는 카탈로그에 없다. 접근성 계약이 선행이다 |

##### 누가 로딩을 알리는가

**영역이 알린다. 자리표시는 장식이다.**

```tsx
<section aria-busy={loading} aria-label="프로젝트 목록">
  {loading ? <Skeleton … /> : <ProjectList … />}
</section>
```

Spinner와 Skeleton은 스스로 읽히지 않는다. 스켈레톤이 여덟 개 놓인 자리에서 각각이 읽히면
같은 말이 여덟 번 들린다. **한 영역이 한 번 말한다.**

끝나면 `aria-busy`가 내려가고 자리표시가 사라진다. 자리표시를 남긴 채 내용을 덧그리지 않는다.

##### reduced-motion

Spinner와 Skeleton 모두 반복이 **1회로 끝난다**(DS-D-0016 — loop는 짧아지는 것이 아니라
사라진다). 로딩 중이라는 뜻은 `aria-busy`와 면이 유지하며 움직임이 그 뜻을 만드는 것이 아니다.

`--palette-gray-000-rgb` 로 갈아끼운다(`NodeCanvasHomeScene.tsx:221`, `NodeCanvasHomeScene.tsx:223`).

**reduced-motion에서 그라디언트가 남는다.** 제품은 애니메이션만 끄고 그라디언트는 그대로 둔다 —
`NodeCanvasHomeScene.tsx:161` 와 `VideoEditScene.tsx:167` 은 미디어 쿼리로, 결제 상태 화면은
`motion-reduce:animate-none` 으로 같은 결과를 낸다(`mypage/upgrade/billing-success/page.tsx:95`).
글자가 계속 `color: transparent` 이므로 정지한 그라디언트가 글자를 그린다. 위 「reduced-motion」의
**1회로 끝난다**와 다르다 — 시머 텍스트는 1회를 돌지 않고 **0프레임에서 멈추고**, 그 자리에서 글자가
20%~88% 알파로 얼룩진 채 남는다. 규범화할 때 이 얼룩을 허용할지 균일 알파로 떨어뜨릴지 판정이
필요하다.

**자리표시가 읽힌다.** `<section aria-live="polite">` 안의 `<span role="status" aria-label={…}>`
구조다(`NodeCanvasHomeScene.tsx:1320-1324`). 영역 구조는 위 「누가 로딩을 알리는가」와 같지만
**자리표시가 `aria-hidden` 이 아니라 읽히는 텍스트**라는 점이 Skeleton과 다르다. 시머 텍스트에
「자리표시는 장식이다」를 그대로 적용하면 로딩 문구가 통째로 사라진다. 결제 상태 화면은 더 나아가
**로딩 동안 제목·설명·오류·메타·액션을 렌더하지 않고 이 단어 하나만 남긴다**
(`mypage/upgrade/billing-success/page.tsx:423-431`) — 카드 안의 장식이 아니라 화면 전체의 상태다.

**흐름 값이 정본과 다르다.**

| 출처 | 주기 | easing |
| --- | ---: | --- |
| `motion-shimmer` — [motion](../foundations/motion.md) | 1.6s | `easing-standard`(가감속) |
| 제품의 시머 텍스트 아홉 곳 | 2.2s | `linear`(등속) |

[DS-D-0017](../governance/decisions/DS-D-0017-keyframe-contract.md)이 loop에 `background-position` 을
허용하므로 **기법 자체는 게이트를 통과한다. 걸리는 것은 값이다.** motion은 「자리표시의 쓸림에는
가감속이 맞으며 제품도 그렇게 쓴다」고 적지만 그것은 **면** 자리표시의 인구조사이고, **텍스트 시머는
아홉 곳이 전부 등속이다.** 1.6s·가감속으로 끌어오든 2.2s·등속을 정본으로 세우든 하나를 골라야 한다.
고르지 않으면 같은 화면에서 [Skeleton](../components/skeleton.md)과 시머 텍스트가 서로 다른 속도로
돈다.

##### Acceptance tests

1. 자리표시는 전부 `aria-hidden`이고 영역이 `aria-busy`를 갖는다.
2. 끝나면 `aria-busy`가 내려가고 자리표시가 사라진다.
3. 모양을 아는 자리와 모르는 자리가 서로 다른 것을 쓴다.
4. reduced-motion에서 Spinner·Skeleton 모두 반복이 1회다.
5. 합성에 접근성 위반이 없다.

##### 남은 것

determinate progress. 인계서 (1c)가 "접근성 계약부터 정해야 한다"로 남겨 두었고 제품 전체에
`role="progressbar"`가 1곳뿐이다. 그것이 서기 전까지 이 패턴은 두 갈래만 소유한다.

## App Shell

- Source: design/patterns/app-shell.md
- Maturity: experimental

### App Shell

App Shell은 로그인 후 제품 화면의 navigation, viewport, main surface, top chrome, global overlay를
소유한다. 기능 Scene은 Shell **안의 콘텐츠**를 소유하며 sidebar 여백이나 viewport 적층을 다시 만들지
않는다.

이 패턴은 로그인 후 archive, creation hub, editor, highlight, analytics, account surface에 적용한다.
마케팅·인증처럼 독립 navigation을 가진 surface는 범위 밖이다.

#### Anatomy

```text
AppShell
├─ Skip link
├─ Navigation rail
│  ├─ Brand / home
│  ├─ Primary navigation
│  └─ Account / plan actions
├─ Mobile navigation scrim
├─ Main surface
│  ├─ Top chrome
│  │  ├─ Navigation toggle
│  │  ├─ Breadcrumb / page title
│  │  ├─ Context actions
│  │  └─ Profile trigger
│  └─ Primary scroll root or workspace host
└─ Global overlay root
```

DOM portal은 이 anatomy를 구현하는 방법 중 하나일 뿐 계약이 아니다. 공용 API는 slot 또는 layout
composition을 우선하되, top chrome이 main surface의 폭·배경·scroll 문맥을 정확히 공유해야 한다.

#### Ownership boundaries

| 소유자                 | 반드시 소유한다                                                                               | 소유하면 안 된다                                       |
| ---------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| App Shell              | viewport height, safe area, sidebar/drawer 상태, main offset, top chrome, global overlay root | 기능별 grid 열 수, editor pane 크기, 프로젝트 데이터   |
| Page pattern           | main surface 안의 section, page scroll content, empty/loading/error 상태                      | sidebar width 계산, body portal의 임의 z-index         |
| Editor Workspace       | workspace host 안의 pane, timeline, local menu와 local overlay                                | navigation rail, profile popover, viewport 전체 offset |
| Dialog/Overlay service | modal inert/focus/scroll lock, semantic overlay layer                                         | 페이지별 임의 숫자 z-index 계약                        |

Shell의 geometry를 바꾸는 기능 요구는 feature 내부 CSS 예외가 아니라 App Shell 변경으로 처리한다.

#### Layout contract

##### Persistent navigation

- navigation rail은 문서 흐름 밖에 있을 수 있지만 main surface가 **같은 sidebar state 원천**으로 자리를
  예약해야 한다.
- expanded, collapsed, editor-auto-collapsed의 어떤 상태에서도 navigation과 main surface가 겹치지
  않는다.
- sidebar 폭 변경 중 main offset과 main width를 따로 지연시키지 않는다.
- main surface의 바깥 여백과 안쪽 content inset은 별도 semantic token으로 관리한다. feature가 음수
  margin으로 sidebar gap을 보정하지 않는다.
- 넓은 화면에서 main surface는 남은 공간을 사용하며 임의 max-width로 프로젝트 목록을 3열에
  고정하지 않는다.

##### Compact navigation

- compact mode에서 sidebar reserve는 0이고 main surface는 전폭이다.
- navigation은 scrim 위 drawer로 열리며 main content를 밀지 않는다.
- drawer가 열리면 뒤 콘텐츠는 pointer와 focus 양쪽에서 비활성화되고 문서 scroll이 잠긴다.
- Escape, scrim activation, navigation 완료로 닫히며 trigger로 focus를 복원한다.
- desktop의 collapsed preference를 compact drawer의 내부 배치에 적용하지 않는다. drawer는 label을
  포함한 expanded navigation이다.

##### Main surface and scroll

- main surface는 page와 navigation 사이의 유일한 제품 작업 면이다.
- regular mode의 surface chrome과 compact mode의 edge-to-edge 표현은 같은 content 구조를 공유한다.
- 일반 page는 한 개의 primary scroll root를 가진다. `body`와 카드 내부가 동시에 세로 scroll하지
  않는다.
- workspace page는 main surface를 고정 host로 제공하고 editor가 내부 scroll을 소유한다.
- sticky top chrome은 primary scroll root와 같은 surface 안에 있어야 한다.
- main content와 top chrome은 동일한 좌우 inset 원천을 읽는다.

  - **예외** — 패널 안에 든 상단 크롬(`mainChromeTopBarInPanel`)은 `--mainchrome-bleed-left/right`로 감싼 요소의 좌우 패딩을 음수 margin으로 상쇄해 카드 전폭으로 번진다. 값과 폴백 트랩은 「아직 토큰이 없는 축」에 있다.

공용 App Shell composition은 하나만 제공하고 page scroll과 workspace host를 명시적인 variant로 둔다.
`<main>`과 시각 panel의 소유권을 variant마다 바꾸지 않는다.

#### Sidebar spacing

간격은 다음 정렬선으로 검증한다. 픽셀을 복사하기보다 semantic token 관계를 보존한다.

1. brand와 navigation item의 leading content line
2. navigation item과 main content의 leading line
3. top chrome과 page section의 horizontal inset
4. main surface의 top/right/bottom outer gap
5. collapsed icon hit area의 optical center

위 관계 대부분에 semantic token이 붙었다(아래 표). 이름과 값이 바뀌어도 **sidebar 내부 padding 변경으로
main inset이 우연히 어긋나지 않게** 관계 테스트를 유지한다. 추출 근거는
[`KP-LAYOUT-001`](../../migration/product-baseline.md)에 있다.

##### 아직 토큰이 없는 축

아래는 **제품이 LOUIS 토큰을 소비하지 않는** 축이다. 「LOUIS 쪽에 값이 없다」는 뜻이 아니다 —
`--app-gnb-main-inline-padding-end`와 `--app-gnb-rail-padding-bottom`은 LOUIS에 **이름까지 같은
토큰이 이미 있고**([tokens.css:232](../../packages/tokens/generated/tokens.css) · `234`) 값도 데스크톱 값(둘 다 `12px`)과 같다. 제품이 받지
않는 이유는 이 두 축이 ≤719px에서 각각 `16px` · `0px`로 갈라지는데 LOUIS 토큰은 단일값이라 그
관계를 담지 못하기 때문이고, 제품이 바로 그 이유를 주석으로 적어 둔다(`globals.css:91` · `107`).
「제품 잔류」 주석 자체는 여섯 곳(`globals.css:86` · `97` · `100` · `107` · `114` · `120`)이지만
반응형 분기를 이유로 드는 것은 이 둘뿐이다 — 나머지 넷은 정렬 관계 · 씬 확장점 · JS 상수 짝 ·
제품 연출 좌표라는 다른 이유다. 옮기는 쪽에서 **지어내지 말고 제품을 인용한다.**

**두 줄은 예외다 — 제품이 실제로 LOUIS에서 값을 받는다.** `--app-shell-min-width`는
`var(--louis-app-shell-min-width)`(960px)이고, 드로어가 쓰는 `--app-gnb-sidebar-padding-x`는
`var(--louis-layout-app-shell-sidebar-padding)`이다(`globals.css:124` · `103`). 그래도 표에 남는
이유는 둘이 서로 다르다. `--app-shell-min-width`는 **≤719px에 아예 적용되지 않는다** — 선언은
`:130`이고 적용은 `@media (min-width: 720px)` 안 `:386`뿐이라 compact 쪽 거동이 토큰 바깥이다.
드로어 패딩은 반응형이 아니다 — `--app-gnb-sidebar-padding-x`는 폭 조건 없이 `:root`에 선언돼
≤719px에서도 `12px` 그대로이고(그래서 표의 데스크톱 칸이 `—`인 것은 「값이 없다」가 아니라

드로어라는 부품이 없다**는 것이다.

**`outer-gap`은 부분만 대응한다.** 제품에는 12px 관계가 셋(상·우·하) 있고 셋이 서로 다른 변수를
갖는다. compact에서 상단만 유지되고 우측은 16으로, 하단은 0으로 갈라지므로 **하나의 토큰으로
셋을 덮을 수 없다.** DS-D-0018이 이 토큰을 「부분」으로 판정한 이유다.

**≤719px에서 바깥 여백은 토큰 값과 무관하게 0이다(2026-08-21 실측).** 위 표의 `12px → 16px` ·
`12px → 0px`는 **토큰 값**이고, 그 값을 읽던 **씬 루트가 compact에서 상·우·하 padding을 하드 `0`으로
덮는다.** 좌 padding은 데스크톱에서도 `0`이다.

**그래서 compact의 16px은 카드 바깥이 아니라 카드 안쪽으로 간다.** compact에서
`--app-gnb-main-inline-padding-end`를 읽는 자리는 전부 카드 안쪽이다 — 카드와 `<main>`의 안쪽
패딩(`appHomeSceneStyles.ts:766` · `myPageSceneStyles.ts:66` · `NodeCanvasHomeScene.tsx:129` ·
`AdminClient.tsx:98`), 카드 안 본문 컬럼(`InstagramAnalyticsScene.tsx:320`), 패널 안 상단
바(`Gnb.tsx:477`)다. **모바일 시안에 카드 바깥 여백을 그리면 틀린다 — 카드가 화면 폭 전체다.**

**드로어의 면은 페이지 배경이 아니다(2026-08-21 실측).** compact에서 드로어는 먼저
`--app-page-bg`를 깔지만 곧바로 테마별 규칙이 덮는데, **라이트만 `--palette-gray-200`으로
갈라진다.** 앱 셸 라이트에서 `--app-page-bg`는 `--palette-gray-100`(`#f8f8f9`)이고 드로어는
`#eeeef1`이므로 **페이지 배경색으로 드로어를 그리면 한 단계 밝게 나온다.** 다크는 둘이 같다.

**드로어 스크림은 dialog scrim과 다른 값이다.** 드로어 스크림은 `rgba(0, 0, 0, 0.4)`로 테마와
무관하게 고정이고, [Dialog](../components/dialog.md)의 `color-dim-modal`(라이트 56% · 다크 72%)과
갈린다. **56%/72%로 대신 그리면 뒤 화면이 한 단계 어둡게 나온다.** 적층도 DS 사다리 밖이다 —
드로어 `z-index: 1400` · 스크림 `1399`(`Gnb.tsx:2073` · `1904`)로 프로필 popover(1100)보다 위이며,
그 이탈은 [App Shell Parts](../components/app-shell-parts.md)의 Known deviations가 기록한다.

**셸 높이는 토큰이 아니라 런타임 주입이다.** `--app-shell-vh`는 CSS 어디에도 정의가 없다.
`AppHomeScene`이 마운트될 때 `Math.round(visualViewport.height ?? innerHeight)`를 px로
`documentElement`에 쓰고 언마운트에서 지운다 — `resize`와 `visualViewport.resize` 두 이벤트로
갱신한다(`AppHomeScene.tsx:263-277`, 주입 `241` · 정리 `249`). 존재 이유는 iOS Safari 등에서
`100dvh`가 실제 가시 높이와 어긋나 고정 높이 셸 아래에 흰 여백이 생기는 것을 막는 것이다. CSS는
언제나 `var(--app-shell-vh, 100dvh)`로 읽으므로 **JS 미실행·하이드레이션 전에는 `100dvh`가 남는다.**
**모바일 프레임 높이를 `100dvh` 상수로 굳히면 제품과 어긋나고, 그 어긋남을 잡아 주는 장치가 없다** —
프레임은 브라우저 크롬을 뺀 실제 가시 높이로 잡고 `100dvh`는 폴백으로만 적는다.

**bleed 두 개는 패널 안 상단 크롬을 카드 패딩 밖으로 되돌린다.** 크롬 바는
`width: calc(100% + 좌 + 우)`와 좌우 `calc(-1 * 같은 값)` margin으로 감싼 요소의 좌우 패딩을 정확히
상쇄해 **카드 전체 폭으로 번진다**(`Gnb.tsx:464-466`). 그래서 값은 언제나 **감싼 요소의 좌우 패딩과
같게** 선언된다 — 형태 B의 `<main>`은 `16px`/`12px`(`myPageSceneStyles.ts:58-59`, 그 패딩 `60`),
결제 결과 카드는 `24px`/`24px`(`billing-success/page.tsx:60`, 그 패딩 `63`)이다. ≤719px에서 형태 B는
`16px`/`16px`로 함께 바뀌고(`myPageSceneStyles.ts:64-65`, 그 패딩 `66`), 결제 결과 카드는 둘 다 `0`이
되어 크롬 바가 본문과 같은 폭이 된다(`billing-success/page.tsx:61`·`58`). **선언하지 않음이 「번짐
없음」이 아니다** — 세 선언의 폴백이 모두 `--app-gnb-main-inline-padding`(16px)이라, 선언을 빼면
우측도 12px(`-end`)이 아니라 16px로 번진다.

**Create 노드 뷰 상단 헤더는 이 인셋 규약 밖이다.** 이 헤더는 `fixed top-0 left-0 right-0`에
`py-4 px-6` 리터럴을 쓰고 `env(safe-area-inset-*)`도 `--app-gnb-main-inline-padding-end`도 참조하지
않는다(`CreateScene.tsx:146-147`, 소비 `673`). `--spacing`이 `2px`이므로 상하 **8px** · 좌우
**12px**이고, 이 헤더에는 719px 분기가 없어 compact에서도 12px 그대로다. **위 표의
`--app-gnb-safe-top`을 따라 상하 12px + safe-area로 그리면 실제 8px과 어긋난다.** 좌우 12px은 우연이
아니다 — 배포본 주석이 「좌우 12px 은 레이어 패널·툴바·줌과 같은 시작선, 상하는 8px」이라고 직접
적는다(`CreateScene.tsx:145`).

##### 메인 카드 표면 — 값은 있고 계약이 없다

카드 표면 자체는 이 패턴이 아니라 제품의 레이어 밖 전역 클래스(`appMainCardChrome` /
`appMainCardChromeSurface`)가 소유하며, **아직 DS 계약이 없다.** 다만 「계약이 없다」가
「값을 모른다」는 뜻은 아니어서, Figma로 옮길 때 지어내지 않도록 실측값을 적어 둔다
(2026-08-21 실측 · 좌표는 `74a7303b` 기준, `globals.css@74a7303b:1316-1397`).

| 축 | 값 | 근거 |
| --- | --- | --- |
| 반경 | `16px` | `globals.css:1334` · `1340` |
| 프레임 | `var(--louis-hairline-inset)` — **0.5px 헤어라인 한 겹, 안쪽(`inset`)**. 글래스 5겹도 `--dropdown-frame`도 폐지됐다 | `globals.css:1430` · `1341` |
| 면 (라이트) | `--palette-gray-100` | `globals.css:1338-1340` · `1345-1347` |
| 면 (다크) | `--palette-gray-800` | `globals.css:1342-1344` · `1349-1351` |
| 스크롤 헤더 슬롯 | `position: sticky; top: 0; z-index: 5` — 하단 페이드(10)보다 **아래**다 | `appHomeSceneStyles.ts:743-751`(sticky·top·z-index는 `751-753`) · `InstagramAnalyticsScene.tsx:336` |
| 하단 페이드 | `::before` `z-index: 10` — `linear-gradient(to top, 면색 100% 0%, 56% 50%, 20% 80%, 0% 100%) bottom / 100% 20px no-repeat` | `globals.css:1362-1369`(공통) · `1362-1371`(라이트) · `1373-1382`(다크) |

**베벨 링(`::after`)은 제품에서 제거됐다.** 이전 판은 이 카드가 프레임 5겹 + 베벨 링 4겹 = 9겹을
갖는다고 적었다. 지금은 **프레임 한 겹뿐**이고, 남은 `::after` 선언은 `≤719px`에서 그 층을
`display: none` 시키던 블록 하나다. 카드 안쪽은 3층이 아니라 **2층이다 — 헤더 슬롯(5) < 하단 페이드(10).**

페이드는 카드가 만든 stacking context 안에 있고 `pointer-events: none` · `border-radius: inherit`을 받는다.

###### 프레임 해결값 — `--louis-hairline-inset`

**제품 토큰 `--dropdown-frame`은 폐지됐다.** 카드는 이제 LOUIS 정본을 직접 소비한다 —
`box-shadow: var(--louis-hairline-inset)`. 제품 저장소 전체에 `--dropdown-frame` **선언**은
0건이다. 다만 이름 자체는 아직 남아 있으니 검색으로 「살아 있다」고 오판하지 않는다 —
`check-tailwind-theme.mjs:194`는 폐지를 적은 **주석**이고, `:239`는 `--dropdown-frame-on-dark`
라는 **다른 토큰**의 금지 패턴이며, `docs/handoff-2026-08-24-louis-hairline-inset.md:52` ·
`66` · `191` · `347`은 폐지 전 상태를 적은 인수인계 문서다. 게이트가 실제로 고정하는 문자열은
`check-tailwind-theme.mjs:199`의 `"box-shadow: var(--louis-hairline-inset);"`이고, 그것은
폐지 확인이 아니라 **LOUIS recipe 소비를 고정**하는 계약이다.

| # | 종류 | inset | x | y | blur | spread | 색 |
| ---: | --- | --- | ---: | ---: | ---: | ---: | --- |
| 1 | 안쪽 헤어라인 | `inset` | `0` | `0` | `0` | `--louis-border-width-hairline` = `0.5px` | `--louis-color-stroke-hairline` |

**테마로 뒤집힌다.** 이전 판은 「라이트에서도 바이트 동일 — 테마 무관」이라고 적었는데, 그것은
`--dropdown-frame` 시절의 성질이다. `--louis-color-stroke-hairline`은 라이트
`color(srgb 0 0 0 / 0.08)`(검정 8%) · 다크 `color(srgb 1 1 1 / 0.08)`(흰 8%)로 **갈린다.**
알파도 옛 12%가 아니라 **8%**다. blur가 `0`이라 드롭섀도우가 아니라 **선**인 것은 그대로다.

**Figma에서는 한 노드에 한 겹으로 그린다** — 카드 노드에 **inner shadow** 0.5px 하나. 바깥
드롭섀도우가 아니다. 오버레이 노드도, 안쪽 베벨도 없다. `elevation-*` 9종 중 일치하는 것은
여전히 **없다** — 이 프레임은 elevation 축이 아니라 `hairline` 축이고, 정의는
[`base.css:21-22`](../../packages/css/src/base.css)에 있다.

**≤719px에서는 프레임과 베벨 링이 통째로 사라진다.** `border-radius: 0` · `box-shadow: none` ·
`overflow: visible`이 되고 `::before`/`::after`가 `display: none`이다(`globals.css:1433-1446`). 형태 B의
`::before`는 전역이 아니라 씬이 끈다(`myPageSceneStyles.ts:94`). **모바일 시안에 카드 프레임을 그리면
틀린다.**

###### 하단 페이드의 출처가 형태마다 다르다

형태 A는 전역 `.appMainCardChrome::before`(`globals.css:1362-1391`)가 준다. 형태 B에는 **그 전역
`::before`가 없고** 씬이 자기 `::before`에 상단·하단 두 배경 레이어를 함께 선언한다 —
`myPageSceneStyles.ts:88`(라이트) · `89`(다크). **출처만이 아니라 값도 갈라져 있다** — 하단
페이드의 가운데 두 스톱이 형태 A는 `56% 50%` · `20% 80%`(`globals.css:1375-1376` 라이트 ·
`1377-1378` 다크)인데 형태 B는 아직 `53% 50%` · `19% 80%`다. **형태 B를 「전역 클래스만 붙이면
된다」로 읽으면 페이드가 통째로 빠지고, 형태 B를 전역 값으로 그리면 스톱이 어긋난다.**

###### 형태 B 전용 상단 페이드 — 값은 적되 켜진 상태로 그리지 않는다

배포본에서 이 페이드가 켜지는 화면은 0개다. 원인은 [제품 확인 사항](../governance/product-confirmations.md)
§7과 [App Shell Parts](../components/app-shell-parts.md)가 기록한다. 값을 남기는 이유는 제품이 고쳤을
때 지어내지 않기 위해서다.

| 축 | 값 |
| --- | --- |
| 방향 | `linear-gradient(to bottom, …)` |
| 스톱 (면색 알파@위치) | `100%@0%` · `98%@30%` · `92%@50%` · `78%@64%` · `55%@76%` · `28%@87%` · `8%@95%` · `0%@100%` |
| 잉크 | 라이트 `--palette-gray-100-rgb` / 다크 `--palette-gray-800-rgb` — 하단 페이드와 같은 면색 |
| 배치·크기 | `top / 100% calc(72px * min(1, var(--header-progress, 0) * 1000)) no-repeat` |
| 실효 높이 | **`0px`** — `--header-progress`가 패널까지 올라오지 않아 언제나 폴백 `0` |

**`min(1, x * 1000)`은 페이드가 아니라 스위치다** — progress가 0을 조금이라도 넘으면 즉시 72px 전체가
켜진다. 제품이 고쳐 켜지는 날이 오면 높이는 상수 `72px`이다.

#### 미결정 — 셸 형태 A / B

**제품에 카드를 거는 방식이 둘이고, 어느 쪽이 정본인지 정해지지 않았다.** 이 문서는 그 사실을
기록만 하며 한쪽을 고르지 않는다. 두 계열은 실제로 공존하고 소비처 수도 비슷하다 —
**한쪽만 그리면 나머지 절반이 시스템 밖이 된다.**

| | 형태 A | 형태 B |

전환 곡선은 양쪽 모두 `320ms cubic-bezier(0.4, 0, 0.2, 1)`로 같다 — 위 표의

소비처는 이렇다(제품 정본 기준 — 커밋은 `migration/product-evidence.lock.json` 의 `productCommit`).

##### 이 문서가 지금 정하지 않는 것

공용 `AppShell` composition의 `variant`(`page` · `workspace`)는 위 A/B와 **같은 축이 아니다.**
`variant`는 스크롤을 누가 소유하는지를 가르고, A/B는 카드가 어느 요소에 걸리는지를 가른다.
둘을 같은 것으로 읽고 매핑하면 한쪽 계열이 조용히 사라진다.

**Figma를 포함해 옮기는 쪽은 한쪽을 골라 굳히지 않는다.** 그리려는 화면이 어느 계열인지 위
표에서 확인하고, 표에 없는 화면이면 「판정 불가」로 보고한다. 결정이 서면 이 절을 결정 기록으로
바꾸고 [DS-D](../governance/decisions/README.md)에 남긴다.

#### Editor route behavior

- immersive editor route에 진입하면 regular mode sidebar를 임시 collapsed로
  만들 수 있다.
- 진입 전 사용자의 상태를 기억하고 route 이탈 시 복원한다. 임시 상태를 영구 preference로 저장하지
  않는다.
- 편집 중 사용자가 sidebar를 직접 전환하면 자동 복원보다 명시적 사용자 선택을 우선한다.
- sidebar를 펼쳐도 workspace host가 재배치되어야 하며 editor 위에 rail을 겹쳐 놓지 않는다.
- compact mode에서는 drawer를 닫은 상태로 workspace에 진입하고, navigation이 필요할 때만 overlay로
  연다.

#### Overlay contract

숫자 `z-index`는 공용 계약이 아니다. 다음 semantic layer의 상대 순서가 계약이다.

| Layer            | 예                                      | 규칙                                                                   |
| ---------------- | --------------------------------------- | ---------------------------------------------------------------------- |
| Surface          | page content, docked editor             | 자기 host 안의 기본 stacking context                                   |
| Local floating   | card menu, editor tooltip, crop handles | 소유 surface 안에서만 경쟁한다                                         |
| Shell chrome     | top chrome, persistent navigation       | docked workspace보다 위지만 modal을 넘지 않는다                        |
| Global non-modal | profile popover, command palette        | shell overlay root에 렌더하고 열려 있는 동안 실제로 선택 가능해야 한다 |
| Modal            | confirm, plan gate, destructive dialog  | 뒤 surface와 non-modal interaction을 막고 focus를 가둔다               |
| Critical system  | session/payment interruption            | 제품 modal보다 위에 둘 필요가 있는 경우에만 별도 정책으로 승인한다     |

- Docked editor root가 viewport-level stacking context를 만들어 profile popover를 가리면 안 된다.
- global popover를 열 때 충돌하는 local menu는 닫는다. modal이 열리면 non-modal popover는 닫거나 inert
  상태가 되어야 한다.
- 보이는 popover 위에 투명한 editor layer가 pointer event를 가로채면 실패다.
- feature overlay가 `document.body`를 직접 선택해야 한다면 global인지 local인지 문서화하고 overlay
  service를 거친다.

#### Responsive matrix

| Mode        | Navigation                          | Main surface                                 | Top chrome                       | Scroll                                           |
| ----------- | ----------------------------------- | -------------------------------------------- | -------------------------------- | ------------------------------------------------ |
| Regular     | persistent expanded/collapsed rail  | rail 다음 남은 영역, surface chrome 유지     | surface 안 sticky                | page 또는 workspace가 하나의 주 scroll 정책 선택 |
| Constrained | persistent rail 또는 임시 collapsed | 기능 패널을 줄이거나 접되 rail과 겹치지 않음 | 주요 액션 유지, 보조 액션 menu화 | body 가로 scroll에 의존하지 않음                 |
| Compact     | reserve 0, overlay drawer           | edge-to-edge                                 | safe area 안에서 유지            | main scroll 한 개, drawer 열림 시 잠금           |

regular/compact 호환 경계와 grid profile은
[Responsive Layout](../foundations/responsive-layout.md)의 Compatibility matrix를 따른다.

#### Accessibility

- navigation은 고유한 `aria-label`을 가진 `<nav>` landmark다.
- 현재 route는 시각 상태와 `aria-current="page"`를 함께 제공한다.
- collapse/drawer trigger는 접근 가능한 이름, `aria-expanded`, `aria-controls`를 가진다.
- main 시작점으로 이동하는 skip link를 첫 keyboard 경로에 둔다.
- top chrome의 시각 순서와 focus 순서를 일치시킨다.
- profile popover는 실제 상호작용 모델에 맞는 menu 또는 dialog semantics를 사용하고, 열기·선택·닫기·
  focus 복원을 keyboard로 완료할 수 있어야 한다.
- sidebar와 main surface 전환은 reduced-motion에서 공간 이동을 최소화한다.

#### Extraction baseline

기존 제품의 App Shell은 sidebar geometry 일부를 공유했지만 Scene별 composition, viewport height와
overlay 숫자가 분산됐다. 비규범 provenance는
[`KP-LAYOUT-001`](../../migration/product-baseline.md)에 보존한다.

보존할 결과는 sidebar 단일 geometry, compact drawer의 zero reserve, immersive route의
collapse/restore다. 복제된 Scene shell, 전역 최소폭, raw z-index는 새 package 계약으로 가져오지 않는다.

#### 구현 (2026-08-18)

공용 composition `AppShell`이 `@klipse-design/react`에 있다. `variant`가 `page`(본문이 구른다)와
`workspace`(에디터가 안쪽 스크롤을 소유한다) 둘이며 **한 composition에 둔다** — 가르면 `<main>`과
시각 panel의 소유권이 variant마다 달라진다.

| 계약 | 구현 |
| --- | --- |
| 자리 예약 | 레일이 `absolute`여도 본문이 **같은 상태 원천**으로 `padding-inline-start`를 잡는다 |
| 전환 | offset과 폭이 `motion-shell-collapse` 하나를 쓴다 — 따로 지연시키면 겹치는 프레임이 생긴다 |
| scroll root | `.louis-app-shell__content` 하나. 셸은 `overflow: hidden` |
| 상단 크롬 | scroll root **안에** sticky. 본문과 같은 좌우 inset 원천을 읽는다 |
| compact | 예약 0 · 레일이 drawer · scrim · 뒤 콘텐츠 `inert` |
| 건너뛰기 링크 | anatomy의 첫 항목. 초점을 받으면 나타난다 |

**접힘 상태는 소비처가 소유한다.** 라우트가 정하는 경우가 있어 셸이 갖지 않는다.

## Landing Shell

- Source: design/patterns/landing-shell.md
- Maturity: experimental

### Landing Shell

Landing Shell은 로그인 전 마케팅 화면의 껍데기다 — 홈 · 가격 · 탐색 · 블로그 · 문서 · 템플릿 ·
법적 고지가 이 하나를 공유한다.

**App Shell과 정반대 모델이다.** 앱 셸은 레일이 자리를 예약하고 본문이 그만큼 밀리지만, 랜딩
헤더는 **자리를 예약하지 않고 콘텐츠 위에 뜬다.** 두 셸을 같은 규칙으로 그리면 랜딩 첫 화면의
윗부분이 헤더에 가려지거나, 반대로 없는 여백이 생긴다.

값은 배포본 인용이며 아직 DS 토큰이 아니다. 간격 환산 기준은 제품의 `--spacing: 2px`다 —
`h-14`는 56px이 아니라 **28px**이다.

#### Anatomy

| 부품 | 역할 |
| --- | --- |
| Blur plate | 헤더 뒤에 깔리는 **고정 120px** 흐림 판. 스크림 없이 글자 가독성을 만든다 |
| Header wrapper | `position: fixed` 투명 껍데기. 패딩만 갖는다 |
| Nav rail | 3열 그리드 — 로고 / 가운데 메뉴 / 우측 액션 |
| Menu list | 가운데 앵커 링크. **720px 미만에서 사라진다** |
| Actions | 언어 글로브 · 상단 CTA · 햄버거 |
| Fullscreen menu | 720px 미만 전용. `<nav>`의 자식이며 `z-index: -1`이다 |

**스크림이 없다.** 헤더는 배경이 `transparent`이고 가독성은 전적으로 blur plate가 만든다.
헤더에 반투명 면을 깔면 배포본과 다르다.

#### Layout contract

| 축 | 값 |
| --- | --- |
| 헤더 | `position: fixed` · `top: 0` · `left: 0` · `width: 100%` · `background: transparent` |
| 헤더 패딩 | `12px 12px 12px 20px` · **≤450px** `12px 16px` |
| 레일 | `display: grid` · `grid-template-columns: 1fr auto 1fr` · `align-items: center` · `min-height: 24px` |
| 레일 전환 | `color 320ms ease` |
| 레일 (≤719px) | `grid-template-columns: 1fr auto` — **가운데 열이 소멸한다** |
| 레일 행 높이 | `min-height`는 하한일 뿐이고 실제 높이는 **최장 액션 컨트롤**이 정한다 — 32px(Button md · LanguageSelector compact) · **≤719px 38px**(햄버거) |
| 1열 로고 | `justify-self: start` · 높이 24px · 폭 `calc(24px × 291 / 85)` = 82.16px |
| 2열 메뉴 | `justify-self: center` · `flex` · `gap: 16px` · **≤719px `display: none`** |
| 3열 액션 | `justify-self: end` · `inline-flex` · `gap: 8px` |
| 3열 액션 · LanguageSelector compact | `36×32` · `padding: 0 8px` · `border-radius: 12px` · globe **20 단독**(라벨도 셰브런도 없다) |
| 메뉴 링크 | 높이 `28px` · `padding-inline: 12px` · `border-radius: 999px` · 면 `transparent` |
| 메뉴 링크 전환 | `color 320ms ease, opacity 200ms ease` |

**헤더가 점유하는 높이는 56px이지만(12 + 32 + 12) 본문에서 예약되지 않는다.** 첫 섹션은 헤더
아래에서 시작하지 않고 **헤더 밑을 지나간다.** 앱 셸의 「레일이 자리를 예약한다」를 여기 적용하면
첫 화면의 구도가 통째로 달라진다.

**가운데 32px은 레일의 `min-height: 24px`가 아니다.** 24px은 하한이고, 행 높이는 액션 열에서
가장 큰 컨트롤이 정한다 — LOUIS Button md 32px(`packages/css/src/component/button.css:67-68` →
`packages/css/generated/tokens.css:467`)와 LanguageSelector compact 32px이 나란히 선다.
**≤719px에서는 상단 CTA가 숨고(`:337`) 햄버거 38px(`:347`)이 최장이 되어 점유 높이가 62px이다.**

근거: `landing/navigation/Gnb.tsx:108-113`(헤더) · `:115-119`(레일) · `:148-151`(로고) ·
`:159-162`(메뉴) · `:164-172`(메뉴 링크) · `:325`(3열 액션) · `:334-338`(상단 CTA) ·
`:346-352`(햄버거) · `tailwind.css:162`(간격 기준). LanguageSelector compact 의 기하는 제품
`LanguageSelector` 의 `TRIGGER`(높이 32) + `TRIGGER_COMPACT`(`padding: 0 8px` · `rounded-12`) +
`ICON_COMPACT`(20)가 갖는다 — 그 파일은 아직 evidence lock 밖이라 줄 좌표로 인용하지 않는다.

#### Blur plate

랜딩 헤더가 가독성을 얻는 **유일한** 장치다. 헤더의 형제이고 한 층 아래에 깔린다.

| 축 | 값 |
| --- | --- |
| 배치 | `position: fixed` · `top/left/right: 0` · `height: **120px**` (고정) |
| 층 | `z-index: 1000` — 헤더(1001) 바로 아래 |
| 포인터 | `pointer-events: none` |
| 흐림 | `var(--louis-progressive-blur-header)` = `blur(12px)` |
| 마스크 | `var(--louis-progressive-blur-mask-header)` = `linear-gradient(to bottom, black 40%, transparent 100%)` — **2스톱** |
| 접두사 | 표준과 `-webkit-`를 **둘 다** 내보낸다 |
| DOM | `<div aria-hidden="true">` 하나. 자식이 없다 |

**값은 LOUIS 가 갖는다**(2026-08-30). 그전에는 흐림 반경과 곡선을 제품이 숫자와 리터럴로
적고 있었다 — 같은 곡선이 제품 다섯 군데에 베껴져 있었고, 그중 `CreativeMediaClient` 는 이
띠와 바이트 동일한 2스톱을 따로 들고 있었다. 반경은 카드 쪽 `blur-surface`(10px)와 **다른 것이
계약**이라 `blur-header`(12px)로 이름을 따로 냈다 — 카드 것을 재사용하면 헤더가 2px 옅어진다.

**120px은 고정값이며 헤더 높이에서 유도되지 않는다.** 헤더 점유 높이(56px)의 배수도 아니고
뷰포트에도 비례하지 않는다 — 어디에서도 계산되지 않는 숫자이므로 바꿀 때 따라 움직일 값이 없다.
마스크는 위에서 40%까지 완전 불투명이고 거기서 아래로 선형 감쇠한다.

**배너 캐러셀의 값을 여기 쓰지 마라.** 그쪽은 `blur(22px) saturate(125%)`에 5스톱 마스크라 흐림이
두 배 가깝게 짙고 감쇠 곡선이 다르다.

근거: `landing/navigation/Gnb.tsx:101-106`(상수) · `:737`(소비처) · LOUIS `packages/css/src/base.css`(두 토큰).

**한때 스크림이 깔려 있었다.** 제품 `66baeb6f`(2026-08-27)가 대비를 벌려고 페이지 바닥색 88%
베일을 이 판에 깔았다 — 위 「스크림이 없다」를 어긴 상태였고, 88% 불투명 판이 흐림을 덮어
progressive blur 가 보이지 않았다. 2026-08-30 소유자 결정으로 걷어내 규범으로 돌아왔다.
그 베일이 풀던 문제(어두운 사진 위 메뉴 글자 1.52:1)는 **닫히지 않았다** — 아래
Tone inversion 이 그 자리다.

#### Tone inversion

랜딩 헤더는 **자기 밑을 지나는 섹션의 밝기에 따라 다섯 가지를 한 덩어리로 뒤집는다.** 이것을
모르면 밝은 섹션 위에서 헤더 글자가 사라진다.

##### 켜지는 조건

`isCapabilitiesTheme || lightSurface || (mobileOpen && 다크 테마가 아님)`

- `lightSurface`는 밝은 배경 페이지에서 **prop으로 영구 고정**된다 — 스크롤과 무관하다.
- 다크 테마의 모바일 메뉴는 **제외**다. 메뉴 면이 어두우므로 헤더는 밝게 남는다.

##### 감지선

`IntersectionObserver`가 `rootMargin: -3% 0px -96% 0px`로 **뷰포트 상단 3~4% 구간의 가로 띠**만
남긴다 — 고정 헤더가 실제로 덮는 자리다. 스크롤 중 reflow를 만들지 않으려고 관찰자로만 판정한다.

대상은 밝은 섹션 **7개**(`overview` · `capabilities` · `video-editor` · `highlight` · `pricing` ·
`faq` · `final-cta`)이고 다크 섹션(히어로 · 쇼케이스)은 제외다. **띠에 닿은 밝은 섹션이 하나라도
있으면 켜진다.**

예외가 하나 있다 — `#overview`는 병합 애니메이션이 대기 상태인 동안 밝은 섹션에서 빠진다.
그래서 그 상태 속성을 함께 감시해 재평가한다.

##### 뒤집히는 다섯

| 부품 | 꺼짐 (어두운 섹션 위) | 켜짐 (밝은 섹션 위) |
| --- | --- | --- |
| 레일 전경 | `--gray-000` — 헤더 안에서 `#fafafa`로 복구 | `--gray-900` |
| 로고 자산 | `klipse-dark.svg` | `klipse-light.svg` |
| 메뉴 링크 | `palette-gray-000` · 비활성 `opacity .7` / hover `.9` | `palette-gray-900` · 비활성 `.65` / hover `.8` |
| 상단 CTA | 면 `--gray-000` · 글자 `gray-900` | 면 `--gray-900` · 글자 `gray-100` |
| 햄버거 | `gray-000` | `gray-900` |

활성 링크는 **양쪽 모두 불투명 1**이다. 전환은 레일·햄버거가 `color 320ms ease`, 로고가
`filter 320ms ease`다.

**밝은 면 위 비활성 링크는 `.65` 아래로 내려갈 수 없다.** 시안 값 `.50`으로 그리면
`palette-gray-900`이 랜딩 바닥(#f1f1f3)과 **3.23:1**이라 14px 본문 기준 AA(4.5)에 못 미친다 —
비활성 컨트롤이 아니라 **누를 수 있는 내비게이션 링크**라 면제 대상이 아니다. `.65`는 5.11:1이고
활성(1.00)과의 간격도 남는다. 어두운 면 위(흰 잉크)는 `.70`에서 이미 9.57:1이라 손대지 않는다 —
**두 톤의 불투명도가 다른 것이 맞다.** 근거: `landing/navigation/Gnb.tsx:189-198`.

**헤더 안에서 `--gray-000`을 팔레트 값으로 되돌린다.** 시맨틱 램프는 테마에서 뒤집히는데 랜딩
헤더는 섹션 밝기로 판정하므로, 두 축이 겹치면 어두운 섹션 위에서 글자가 검게 나온다.

근거: `landing/navigation/Gnb.tsx:87-104` · `:370-375` · `:399-400` · `:611` · `:622-627` ·

#### Layer order

**랜딩 GNB는 semantic layer를 쓰지 않고 실수를 직접 쓴다.** [Elevation & Layer](../foundations/elevation-layer.md)가
금지한 「공용 순서 사이의 임의 숫자」에 해당하므로 **부채로 기록한다.** 다만 화면을 그리려면 실제
순서를 알아야 한다.

| 층 | 값 | 비고 |
| --- | ---: | --- |
| 드롭다운 패널 (body portal) | **2000** | **인라인 style**이 클래스의 `z-20`을 이긴다 |
| 헤더 | 1001 | |
| Blur plate | 1000 | |
| `<nav>` | 2 | `position: relative` — 여기서 stacking context가 생긴다 |
| 풀스크린 모바일 메뉴 | **−1** | `<nav>`의 **자식**이다 |

##### 음수 오버레이 관용구

모바일 메뉴는 `position: fixed; inset: 0; z-index: -1`이면서 `<nav>`의 자식이다. `<nav>`가
`relative` + `z-index: 2`로 자체 stacking context를 만들기 때문에 **`z: -1`이 밖으로 새지 않고
nav의 배경 층에 갇힌다.**

그 결과 **nav의 다른 자식인 로고와 햄버거가 메뉴 위에 남아 계속 눌린다** — 그것이 유일한 닫기
수단이다. 오버레이가 포인터를 가로채지 않는다는 점에서 규범을 만족시키지만, **방식이 규범이
기술한 것과 다르다.**

**판정이 필요하다.** 이 관용구를 `layer-*`의 대응 항목으로 인정할지, 부채로 보고 오버레이를 위로
올린 뒤 별도 닫기 버튼을 두게 할지. 정하지 않으면 화면을 조립할 때마다 다시 발명된다.

근거: `landing/navigation/Gnb.tsx:870`(드롭다운 패널의 인라인 `zIndex: 2000`) · `:223`(같은 패널의
클래스 `z-20` — 인라인이 이긴다) · `:108`(헤더 1001) · `:101`(blur plate 1000) · `:116`(`<nav>`의
`relative` + `z-2`) · `:382-386`(풀스크린 메뉴 `fixed inset-0 z-[-1]`).

| blur plate 높이 | `120px` | `landing/navigation/Gnb.tsx:102` |
| blur plate 흐림 | `blur(12px)` | `:102` — **소비처다.** 값은 아래 |
| blur plate 마스크 | 2스톱 `40% → 100%` | `:103-104` — **소비처다.** 값은 아래 |
| 헤더 패딩 | `12px 12px 12px 20px` (≤450px `12px 16px`) | `:109` · `:111` |
| 톤 전환 길이 | `320ms ease` | `:117` |
| 감지 띠 | `rootMargin: -3% 0px -96% 0px` | `:653-657` |

**흐림과 마스크 두 줄은 2026-08-30에 닫혔다.** 그날 이 자리가 자기 이름을 얻었다 —
`--louis-blur-header`(12px, `packages/css/generated/tokens.css:240`)와
`--louis-progressive-blur-header` · `--louis-progressive-blur-mask-header`
(`packages/css/src/base.css`)다. 표면 흐림(`blur-surface` 10px)과 **같은 축으로 묶지 않은 것이
판정의 내용**이다 — 화면에 고정된 띠는 뒤로 지나가는 것이 카드보다 크고 빨라 한 단 더 흐려야 한다.
그래서 위 두 줄의 근거는 값이 아니라 **제품이 그 변수를 읽는 자리**를 가리킨다. 두 줄을 표에
남겨 두는 이유는 값의 출처가 두 저장소에 걸쳐 있다는 사실 자체가 화면을 그릴 때 필요해서다.

#### Accessibility

- blur plate는 `aria-hidden="true"`이며 포인터를 받지 않는다.
- 가운데 메뉴는 720px 미만에서 DOM에서 사라진다(`display: none`) — 접힘이 아니라 **소거**다.
  앱 셸이 「이름은 남긴다」로 처리하는 것과 다르다.
- 모바일 메뉴가 열려 있을 때 로고와 햄버거가 계속 도달 가능하다. **닫기 버튼이 따로 없다.**

#### Acceptance tests

1. 헤더가 본문 자리를 예약하지 않는다 — 첫 섹션이 헤더 밑을 지나간다.
2. blur plate가 120px 고정이고 뷰포트 높이에 비례하지 않는다.
3. 밝은 섹션이 상단 띠에 닿으면 다섯 부품이 **함께** 뒤집힌다. 하나만 뒤집히지 않는다.
4. `lightSurface` 페이지에서는 스크롤과 무관하게 켜진 상태로 고정된다.
5. 720px 미만에서 가운데 메뉴가 DOM에서 사라지고 레일이 2열이 된다.
6. 모바일 메뉴가 열려도 로고·햄버거가 눌린다.
7. 드롭다운 패널이 헤더 위에 그려진다 — 인라인 층이 클래스를 이긴다.

#### Pre-implementation blockers

- **음수 오버레이 관용구의 판정**(위 Layer order). 인정할지 부채로 볼지 정해야 한다.
- **blur plate가 `backdrop-filter` 축인지 표면 흐림 축인지.** DS의 blur primitive와 같은 축이면
  토큰을 공유하고, 아니면 별도 축을 세운다.
- **톤 반전을 mode로 볼 것인가.** 라이트/다크 mode와 직교하는 **세 번째 축**이다 —
  [Color & Theme](../foundations/color-theme.md)의 mode 계약은 이 축을 모른다.

#### 승격 조건

- 위 세 blocker가 닫힌다.
- blur plate · 헤더 패딩 · 톤 전환 길이가 semantic token으로 선다.
- 그 전까지 이 문서의 값은 **제품 인용**이며 DS 계약이 아니다.

## Auth Two Panel

- Source: design/patterns/auth-two-panel.md
- Maturity: experimental

### Auth Two Panel

로그인 전 인증 화면의 껍데기다. **좌 브랜드 패널 + 우 폼 패널**의 2열이고, 720px 미만에서
브랜드 패널이 통째로 사라져 폼만 1열 가운데에 남는다.

**전환점은 720px 하나뿐이다.** 그 밖의 분기는 슬로건 타입 스케일(1200px) 하나다.

값은 배포본 인용이다. **색과 곡률 축은 이미 LOUIS 시맨틱으로 서 있고**(브랜드 면 · 슬로건 전경 ·
eyebrow 네 축), 남은 기하 축은 아직 DS 토큰이 아니다. 간격 환산 기준은 제품의 `--spacing: 2px`다 —
`p-10`은 40px이 아니라 **20px**이다.

#### 소비처 — 공용 하나와 복제 셋

**8개 화면이 이 껍데기를 쓰는데 경로가 둘이다.** 이 사실이 이 패턴의 첫 규칙이다.

| 경로 | 화면 |
| --- | --- |
| 공용 `AuthStatusCard` 사용 (5) | `/reset-password` · `/reset-password/new` · `/signup/check-email` · `/signup/expired` · `/signup/verified` |
| **같은 셸을 자기가 복제** (3) | `/login` · `/signup` · `/aws/signup` |

**복제 셋은 공용 컴포넌트를 쓰지 않고 같은 상수를 자기 파일에 다시 적는다.** 그리고 **이미
갈렸다** — 좁은 폭 페이지 패딩(공용 20px / 복제 16px), 카드 세로 간격(`/login`만 28px), 로고
아래 여백과 높이, 제목 `letter-spacing`이 경로에 따라 다르다. 아래 표는 그 갈림을 축마다
적는다. Figma로 옮길 때는 **하나의 컴포넌트로 그리고**, 복제가 있다는 사실과 갈린 축을
알려진 부채로 남긴다.

#### Anatomy

| 부품 | 역할 |
| --- | --- |
| Page root | `100svh` 그리드. 720px에서 1열 ↔ 2열이 갈린다 |
| Brand panel | 좌측. 파란 면 + 배경 SVG + 상단 심볼 · 하단 슬로건 |
| Form panel | 우측. **좁은 폭에서는 `display: contents`로 사라진다** |
| Form card | 실제 폼. 최대 400px |
| Eyebrow | 폼 위의 알약 라벨 |
| Form header | 제목 + 설명 한 덩어리. 내부 간격 `8px`(`gap-4`) · 설명 `max-width: 340px` · `fg-secondary` · body-16. 공용은 항상 보이고 `/login` · `/signup`은 ≤719px에서 숨는다 |
| Form children | 폼 본문 래퍼. **카드 간격과 별개 축이다** — 공용 `10px`(`gap-5`) · `/login` · `/signup` `14px`(`gap-7`) |
| Logo link | **좁은 폭 전용.** 720px 이상에서 숨는다 |

#### Layout contract

##### Page root

| 축 | ~719px | ≥720px |
| --- | --- | --- |
| 높이 | `min-height: 100svh` | 같음 |
| 배치 | `grid` · `place-items: center` | `grid-template-columns: minmax(0, 1fr) minmax(0, 1fr)` · `place-items: stretch` |
| 패딩 | `20px` — 복제 셋(`/login` · `/signup` · `/aws/signup`)만 `16px` | `20px` |
| 열 간격 | — | `20px` |
| 면 | `--gray-900` | 같음 |

**`minmax(0, 1fr)`을 `1fr`로 바꾸면 안 된다.** 최소 크기를 0으로 눌러야 긴 슬로건이 열을 밀지
않는다.

##### Brand panel (좌)

| 축 | 값 |
| --- | --- |
| ~719px | `display: none` — **DOM에 남지만 그려지지 않는다** |
| ≥720px | `flex column` · `align-items: flex-start` · `justify-content: space-between` |
| 패딩 · 곡률 | `20px` · `12px` |
| 면 | `--louis-color-accent-primary` (`bg-accent-primary`) = `#0088ff` — light · dark 같은 값이라 테마 분기가 없다 |
| 배경 이미지 | `/footer-logo-bg.svg` · `background-size: 100% 100%` · `no-repeat` · `center` |
| 클리핑 | `overflow: hidden` · `min-width: 0` |

**면 색은 리터럴이었지만 2026-08-24 배포본에서 시맨틱으로 옮겨 갔다.** 예전에는
`bg-[#0093ff]`였고 이 문서도 그렇게 적었는데, 지금은 `bg-accent-primary`다
(`AuthStatusCard.tsx:27` · `login/page.tsx:43` · `app/signup/page.tsx:37`).
`--louis-color-accent-primary`는 light · dark 두 mode가 같은 `#0088ff`라 **테마 분기가 없다는
성질은 그대로다** — 브랜드 면이므로 램프를 따라가지 않는다. `#0093ff`는 배포본 코드에 더는
없고 `/node-canvas.svg` 같은 자산 파일 안에만 남아 있다.

`/aws/signup`만 이 축이 갈린다 — 코브랜드 주황 `#ff9900` 리터럴에 자기 배경 사진을 얹는다
(`aws/signup/page.tsx:89`).

`background-size: 100% 100%`이라 **배경 SVG가 비율을 유지하지 않고 늘어난다.** 열 비율이 바뀌면
그림도 함께 왜곡된다 — 의도된 동작이다.

내용은 둘뿐이다.

| | 값 |
| --- | --- |
| 상단 심볼 | `display: none` → ≥720px `block` · `line-height: 0` |
| 하단 슬로건 | `max-width: 18ch` · 색 `--louis-color-fg-inverse` (`text-fg-inverse`) · `margin: 0` |
| 슬로건 (≥1200px) | 타입이 `heading-48`로 **승급**한다 (size · line-height · letter-spacing 셋 다) |

슬로건 색도 리터럴 팔레트에서 역할 이름으로 옮겨 갔다 — 예전 `text-palette-gray-000`이 지금은
`text-fg-inverse`다(`AuthStatusCard.tsx:41` · `login/page.tsx:63`). 두 토큰의 해석값은 light ·
dark 모두 `#fafafa`로 같으므로 **렌더는 변하지 않는다.** 이름만 제품과 어긋나 있었다.
`/aws/signup`은 여전히 `text-palette-gray-000`이다(`aws/signup/page.tsx:101`).

##### Form panel (우)

| 축 | ~719px | ≥720px |
| --- | --- | --- |
| 표시 | **`display: contents`** | `grid` · `place-items: center` |
| 패딩 | — | `clamp(32px, 6svh, 72px) 32px` |
| 스크롤 | — | `overflow-y: auto` |

**`display: contents`가 좁은 폭에서 래퍼를 지운다.** 그래야 폼 카드가 페이지 그리드의
`place-items: center`를 **직접** 받는다. 래퍼를 남기고 안에서 가운데 정렬하면 카드가 세로로
가운데 오지 않는다.

##### Form card

| 축 | ~719px | ≥720px |
| --- | --- | --- |
| 폭 | `min(100%, 400px)` | 같음 |
| 배치 | `grid` · `justify-items: center` · `text-align: center` | 같음 |
| 세로 간격 | `8px` (`gap-4`) | **`24px`** (`gap-12`) — `/login`만 `28px`(`gap-14`) |
| 제목 | `type-heading-28-medium` | 같음 |

**세로 간격이 세 배가 된다.** 좁은 폭의 촘촘한 리듬을 넓은 폭에 그대로 쓰면 폼이 뭉쳐 보인다.

`--spacing: 2px` 격자라 `gap-12`는 **24px**이다. 8화면 중 7이 24px이고
(`AuthStatusCard.tsx:55` · `app/signup/page.tsx:65` · `aws/signup/page.tsx:120`),
`/login` 하나만 `gap-14` = **28px**이다(`login/page.tsx:81`).

**하단 링크의 음수 마진은 그 28px 전용이다.** `/login`이
`[@media(min-width:720px)]:mt-[-12px]`로 폼과 하단 링크를 당기는 것은 자기 카드 간격이 28px이기
때문이고, 주석도 「데스크톱에선 카드 gap(28px)이 커서」라고 적는다
(`login/page.tsx:201-206`). 24px인 나머지 일곱에는 그 보정이 없다 — **공용 규칙으로 옮기면
안 된다.**

제목 타입은 8화면이 전부 같다(`AuthStatusCard.tsx:134` · `login/page.tsx:363` ·
`app/signup/page.tsx:392` · `aws/signup/page.tsx:452`). 다만 **복제 셋만** 제목에
`letter-spacing: 0`을 덧대 스케일의 자간을 지운다(`login/page.tsx:95` ·
`app/signup/page.tsx:78` · `aws/signup/page.tsx:134`) — 공용 `AuthStatusCard`는 덧대지 않는다.
복제 부채이지 이 패턴의 계약이 아니다.

##### Eyebrow

| 축 | 값 |
| --- | --- |
| 배치 | `inline-flex` · 가운데 정렬 |
| 최소 높이 | `30px` |
| 곡률 | `999px` — `--louis-radius-pill` (`rounded-pill`) |
| 테두리 | `1px solid` `--louis-color-stroke-subtle` |
| 면 | `--louis-color-bg-surface` |
| 패딩 | `0 12px` |
| 글자 | `--louis-color-fg-tertiary` |

**이 네 축은 이미 LOUIS로 수렴했다.** 예전 값은 알파 리터럴이었다 — 테두리
`rgb(var(--gray-000-rgb) / 10%)` · 면 `/ 4%` · 글자 `/ 58%`, 곡률 `9999px`. 지금 제품은
`rounded-pill` · `border-stroke-subtle` · `bg-bg-surface` · `text-fg-tertiary`를 쓴다
(`AuthStatusCard.tsx:70-72`). `rounded-pill`은 `--radius-pill` → `--louis-radius-pill`이고 값은
`999px`이라, 「원본이 `9999px`이므로 바꾸지 않는다」는 옛 단서는 **더 볼 필요가 없다.**

**LOUIS `.louis-badge`는 채택하지 않는다.** 정본 배지는 면으로 상태를 전달하는 채워진 형태
(반경 8 · 상하 4 좌우 8 · `bg-inset` · `fg-secondary` · caption 400)이고, 이 eyebrow는 면 없이
테두리로만 서는 알약 라벨이다 — 여덟 축이 전부 갈려 껍데기를 쓰면 정본 값을 하나도 남기지
못한다(`AuthStatusCard.tsx:63-73`).

##### Logo link

**좁은 폭 전용이다.** `≥720px`에서 숨는다 — 넓은 폭에서는 좌 패널의 브랜드 심볼이 그 역할을 한다.

**Form card의 첫 자식이다**(`AuthStatusCard.tsx:118-125` · `login/page.tsx:353-359`). 그래서 아래
여백이 카드 세로 간격과 **합산된다** — 공용은 `mb-8`(16px) + 좁은 폭 카드 간격 8px = 실효
**24px**이다(`AuthStatusCard.tsx:59`). `/login` · `/signup`은 `mb-12`(24px)이라 실효 32px이다
(`login/page.tsx:85` · `app/signup/page.tsx:69`). `/aws/signup`에는 로고 링크가 아예 없다 —
파트너십 행이 그 자리를 쓴다.

로고 높이도 갈린다 — 공용과 `/signup`은 `56`(`AuthStatusCard.tsx:122-123` ·
`app/signup/page.tsx:386-387`), `/login`만 `72`다(`login/page.tsx:216`).

`transition: opacity 180ms ease-in-out`, hover `0.84`는 공용 값이다(`AuthStatusCard.tsx:59`).
`/signup`은 `180ms ease` · hover `0.8`이고(`app/signup/page.tsx:69`) `/login`은 전이도 hover도
두지 않는다(`login/page.tsx:85`).

**hover에 `@media (hover: hover)` 가드가 없다** — 터치 기기에서도 발동한다. 원본 모듈 CSS의
맨 `:hover`를 보존한 결과다.

#### 아직 토큰이 없는 축

| 축 | 값 |
| --- | --- |
| 폼 패널 패딩 | `clamp(32px, 6svh, 72px) 32px` |
| 슬로건 폭 | `18ch` — 문자 단위이고 px로 환산하지 않는다 |
| 카드 최대 폭 | `400px` |

`6svh`와 `18ch`는 **뷰포트·글자 단위**라 px 토큰으로 승격되지 않는다. Figma로 옮길 때는 대표
해를 하나 골라 적고 단위를 함께 남긴다.

**이 표에서 두 축이 빠졌다. 지워진 것이 아니라 닫혔다.**

| 닫힌 축 | 옛 값 | 지금 |
| --- | --- | --- |
| 브랜드 면 | `#0093ff` 리터럴 | `--louis-color-accent-primary` (2026-08-24 배포본) |
| eyebrow 곡률 | `9999px` | `--louis-radius-pill` = `999px` (`rounded-pill`) |

#### Responsive matrix

| 폭 | 브랜드 패널 | 폼 패널 | 로고 링크 | 카드 간격 |
| --- | --- | --- | --- | --- |
| ~719px | 없음 | `display: contents` | 보임 | 8px |
| 720~1199px | 보임 | 2열 우측 | 숨김 | 24px (`/login` 28px) |
| ≥1200px | 슬로건 `heading-48` | 같음 | 숨김 | 24px (`/login` 28px) |

#### Accessibility

- 브랜드 패널은 `display: none`이라 **좁은 폭에서 접근성 트리에서도 사라진다.** 정보를 담지
  않으므로 의도된 동작이다.
- 로고 링크는 좁은 폭에서만 나타나고 넓은 폭에서는 브랜드 심볼이 대신한다 — **둘 중 하나는
  항상 있다.**
- 폼 카드가 `text-align: center`다. 긴 오류 문구도 가운데 정렬된다.

#### Acceptance tests

1. 720px 경계에서 1열 ↔ 2열이 갈린다. 그 밖의 폭 분기는 슬로건 타입(1200px)뿐이다.
2. 좁은 폭에서 폼 패널이 `display: contents`이고 카드가 페이지 그리드에서 직접 가운데 온다.
3. 브랜드 면이 테마와 무관하게 `--louis-color-accent-primary`(`#0088ff`)다 — `/aws/signup`만
   코브랜드 주황으로 갈린다.
4. 카드 세로 간격이 8px → 24px로 바뀐다. `/login`만 28px이고, 그 화면에서만 하단 링크에 음수
   마진이 따라온다.
5. 로고 링크와 브랜드 심볼이 동시에 보이지 않고, 동시에 사라지지도 않는다.
6. 슬로건이 1200px에서 `heading-48`로 승급한다.

#### Pre-implementation blockers

- **복제 셋을 공용으로 합칠 것인가.** `/login` · `/signup` · `/aws/signup`이 같은 상수를 자기
  파일에 다시 적는다. 합치는 것은 제품 변경이라 여기서 정하지 않는다.
- ~~**`#0093ff`를 브랜드 토큰으로 세울 것인가.**~~ **제품이 닫았다(2026-08-24).** 브랜드 면이
  `bg-accent-primary`로 옮겨 가 `--louis-color-accent-primary`를 소비한다
  (`AuthStatusCard.tsx:27`). 여기서 결정할 것이 남아 있지 않다.

#### 승격 조건

- 위 두 blocker가 닫힌다 — 브랜드 면은 닫혔고 **복제 셋 통합만 남았다.**
- 카드 폭 · 간격이 semantic token으로 선다. **eyebrow는 닫혔다** — 색 세 축과 곡률이
  `stroke-subtle` · `bg-surface` · `fg-tertiary` · `radius-pill`로 이미 서 있다.
- 그 전까지 이 문서의 값은 **제품 인용**이며 DS 계약이 아니다.

## Status Result

- Source: design/patterns/status-result.md
- Maturity: experimental

### Status Result

결제·구독의 **결과 화면**이 공유하는 콘텐츠 컬럼이다 — 성공 · 실패 · 처리 중 · 결제수단 변경
결과 등 일곱 화면이 같은 뼈대를 쓴다.

**셸이 아니다.** 이 화면들은 [App Shell](../patterns/app-shell.md)의 메인 카드 안에 들어간다. 이 문서가
소유하는 것은 **그 카드 안의 컬럼**이다.

값은 배포본 인용이며 아직 DS 토큰이 아니다. 간격 환산 기준은 제품의 `--spacing: 2px`다 —
`h-20`은 80px이 아니라 **40px**이다.

#### Anatomy

| 부품 | 역할 |
| --- | --- |
| Column | `min(520px, 100%)` 가운데 컬럼. **세로 리듬이 하나뿐이다** |
| Title | `heading-36` medium |
| Description | `body-16` · 전경 56% |
| Alert | 결제 결과 처리 중 잡힌 오류를 알리는 붉은 배너. **제목·설명 다음, Meta list 앞**이다 |
| Meta list | `dt`/`dd` 행 목록. 900px에서 세로로 접힌다 |
| Actions | **전폭 버튼**이 세로로 쌓인다 |

#### Layout contract

| 축 | 값 |
| --- | --- |
| 폭 | `min(520px, 100%)` |
| 정렬 | `align-self: center` |
| 배치 | `flex column` |
| 세로 간격 | **`24px` 하나뿐** — 부품마다 다른 간격을 두지 않는다 |
| 면 · 테두리 · 곡률 · 패딩 | **없다.** 컬럼은 투명하다 |

**컬럼 자체는 아무것도 그리지 않는다.** 면과 곡률은 바깥 메인 카드가 갖는다. 컬럼에 카드를 또
그리면 배포본에 없는 이중 면이 된다.

##### 상단 오프셋이 상태에 따라 갈린다

| 상태 | 오프셋 |
| --- | --- |
| 기본 | `margin-top: clamp(56px, 10vh, 120px)` |
| 기본 (≤900px) | `56px` 고정 |
| **처리 중** | `margin-top: 0` · `flex: 1 1 auto` · `justify-content: center` |

**처리 중에는 위에서 밀지 않고 카드 안에서 세로 중앙에 온다.** 두 상태는 상호배타이며 같은
화면이 로딩에서 결과로 넘어갈 때 컬럼이 위로 올라붙는다.

#### Specification

##### Title · Description

| | 값 |
| --- | --- |
| 제목 | `heading-36` size · line-height · `--type-weight-medium` · 전경 `--gray-000` |
| 제목 줄바꿈 | `break-keep` + `overflow-wrap: break-word` |
| 설명 | `body-16` · 전경 `rgb(var(--gray-000-rgb) / 56%)` |
| 설명 줄바꿈 | `white-space: pre-line` — **문구의 줄바꿈이 그대로 살아난다** |

설명이 `pre-line`이므로 **문구에 든 개행이 렌더에 나타난다.** 문구를 한 줄로 합치면 화면이 달라진다.

##### Alert (결과 처리 오류)

| 축 | 값 |
| --- | --- |
| 패딩 | `12px 16px` |
| 곡률 | `12px` |
| 면 | `rgb(var(--accent-red-500-rgb) / 8%)` |
| 테두리 | `1px solid rgb(var(--accent-red-500-rgb) / 16%)` |
| 글자 | `--accent-red-500` · `body-14` |

**노드 인라인 오류 배너와 비율이 다르다.** 그쪽은 면 10% / 테두리 20% / 두께 0.5px이고 여기는
**면 8% / 테두리 16% / 두께 1px**이다. 두 자리를 한 값으로 통일하지 않는다.

**「실패 전용」이 아니었다(2026-08-30 정정).** 이 배너가 실재하는 자리는 **성공 라우트 하나**다 —
정기결제 성공 화면이 결제는 통과했는데 구독 반영에서 오류가 잡혔을 때 그 사유를 이 배너로 띄운다
(`billing-success/page.tsx:437`, 상수 선언은 같은 파일 :108). 반대로 업그레이드 실패 · 정기결제
실패 · 결제수단 변경 실패 세 화면에는 **배너가 없고** code · message · orderId 를 아래 Meta list
행으로 보여 준다. 「실패 화면 전용」으로 읽으면 실패 화면에 없는 부품을 그리게 된다.

**순서가 계약이다.** 배너는 **제목·설명 다음 · Meta list 앞**에 온다. 컬럼 맨 위가 아니다 —
사용자가 어느 화면인지 먼저 읽고 그다음에 사유를 읽는다. 순서를 적어 두지 않으면 배너를 맨 위에
그려도 문서로는 틀렸다고 말할 수 없다.

**LOUIS 안에 붉은 배너 사양이 두 벌이다.** [Alert](../components/alert.md)의 정본은 체크아웃 오류
배너(면 12% · 테두리 24% · 반경 20 · 가로 18)이고, 위 표는 그것과 값이 다른 별개의 배너다(면 8% ·
테두리 16% · 반경 12 · 가로 16). **이 화면의 배너는 `.louis-alert` 레시피를 쓰지 않는다** — Alert
문서가 열거하는 제품 소비처 다섯 자리에 결과 화면이 없다. 두 벌은 서로 다른 자리의 서로 다른
값이며 통일 대상이 아니다. 한쪽을 고칠 때 다른 쪽을 함께 본다.

##### Meta list

| 축 | ~900px | ≥901px |
| --- | --- | --- |
| 행 배치 | `flex column` | `flex` · `justify-content: space-between` · `align-items: center` |
| 행 간격 | — | `16px` |
| 행 패딩 | `12px 0` | 같음 |
| 행 구분선 | `1px solid rgb(var(--gray-000-rgb) / 8%)` — **마지막 행은 없다** | 같음 |
| `dd` 정렬 | `text-align: left` | `text-align: right` |

**행 간격 16px 은 그림으로 재현되지 않는다.** 행이 `justify-content: space-between`이라 이 gap 은
**최소 간격**으로만 작동하는데, Figma 는 `primaryAxisAlignItems`가 `SPACE_BETWEEN`이면
`itemSpacing`을 무시한다 — 값은 저장되지만 렌더에 나타나지 않는다. 이 저장소의 실측도 같은 이유로
SPACE_BETWEEN 컨테이너의 간격을 0으로 센다([Figma 화면 조립](../governance/figma-screen-assembly.md)의
오탐 표). 그러니 이 축은 **CSS 가 정본이고 Figma 는 대조 대상이 아니다.**

| | `dt` (키) | `dd` (값) |
| --- | --- | --- |
| 크기 | `body-14` = 14px | `body-14` = 14px |
| 굵기 | regular | regular |
| 전경 | `rgb(var(--gray-000-rgb) / 48%)` | `--gray-000` |
| line-height 토큰 | `--type-body-16-line-height` | `--type-body-14-line-height` |
| **렌더 행간** | **21px** | **21px** |

**행간 토큰의 이름은 다르지만 렌더 결과는 같다.** 두 토큰 모두 값이 무단위 `1.5`이고 글자 크기가
둘 다 14px이므로 `14 × 1.5 = 21px`로 동일하다. **「키가 값보다 높은 행 박스를 갖는다」고 읽으면
틀린다** — 이름 차이는 실효가 없는 저작 흔적이다.

**둘 다 굵기를 선언하지 않는다.** 배포본이 `dt`·`dd` 어디에도 `font-weight`를 얹지 않아 둘 다
`body`의 `--type-weight-regular`를 그대로 받는다. `dt`를 medium 으로 그리면 배포본과 다르다 —
키와 값의 대비를 만드는 것은 굵기가 아니라 **전경 알파**(48% ↔ 100%)다.

무단위 line-height는 **자기 요소의 글자 크기에 곱해진다.** 토큰 이름의 숫자(16)가 아니라 그
요소의 크기(14)가 기준이다.

##### Actions

| 축 | 값 |
| --- | --- |
| 배치 | `flex` · `flex-wrap` · `gap: 10px` · `margin-top: 8px` |
| 버튼 폭 | **`width: 100%`** |
| 버튼 높이 | `32px` |
| 버튼 패딩 | `0 12px` |
| 버튼 곡률 | `12px` |
| 버튼 글자 | `body-14` · `--type-weight-regular` |
| 버튼 전환 | `background-color 140ms ease, transform 120ms ease, opacity 140ms ease` |

**버튼 높이·패딩이 낡아 있었다(2026-08-30 정정 — `40px` · `0 20px`).** 배포본은 결과 화면 전부
`h-16 py-0 px-6`이고, 이 문서 첫머리의 환산 기준(`--spacing: 2px`)으로 **32px · `0 12px`**이다
(`billing-success/page.tsx:141`·149, 업그레이드 실패 화면도 같은 상수 모양이다). 두 값은 LOUIS 의
`button-height-md`(32px) · `button-padding-inline-md`(12px)와 같고, `0 20px`은 LOUIS 어디에도 없는
값이었다. 40px 은 사다리에서 사라진 값이 아니라 `lg` 칸이며
([DS-D-0027](../governance/decisions/DS-D-0027-control-size-ladder.md)), 이 화면이 쓰는 칸이 아니다.

**버튼이 전폭이라 `flex-wrap`과 함께 세로로 쌓인다.** 가로로 나란히 놓이지 않는다 — 결과 화면의
액션은 나란한 한 쌍이 아니라 **위아래 목록**이다.

| | primary | secondary |
| --- | --- | --- |
| 면 | `--gray-000` | `rgb(var(--palette-gray-000-rgb) / 8%)` |
| 글자 | `--gray-900` | `--gray-000` |
| hover 면 | `rgb(var(--gray-000-rgb) / 90%)` | `rgb(var(--palette-gray-000-rgb) / 14%)` |
| active 면 | `rgb(var(--gray-000-rgb) / 82%)` | `rgb(var(--palette-gray-000-rgb) / 18%)` |
| active 변형 | `scale(0.98)` | 같음 |

**secondary만 팔레트 잉크를 쓴다.** primary는 시맨틱 `--gray-000`이라 테마에서 뒤집히고
secondary는 `--palette-gray-000`이라 **양쪽 테마에서 흰 잉크로 고정**된다. 한쪽으로 통일하면
한 테마에서 면이 사라진다.

#### 아직 토큰이 없는 축

| 축 | 값 |
| --- | --- |
| 컬럼 폭 | `min(520px, 100%)` |
| 상단 오프셋 | `clamp(56px, 10vh, 120px)` (≤900px `56px`) |
| 컬럼 세로 간격 | `24px` |
| 액션 간격 | `10px` |
| 900px 분기 | 이 화면 전용 — 셸의 719px과 **다른 경계다** |

**900px은 셸의 경계가 아니다.** [Responsive & Layout](../foundations/responsive-layout.md)의 승인된
경계에 없는 값이며 이 화면 계열이 자기 용도로 둔 것이다. 셸 경계로 착각하면 다른 화면까지 접힌다.

#### Accessibility

- **메타 목록은 `<dl>`/`<dt>`/`<dd>`다.** 키–값 쌍이므로 표가 아니라 정의 목록이며, 900px에서
  세로로 접혀도 쌍의 연결이 유지된다.
- **처리 중 상태가 진행률을 주지 않는다.** 남은 시간을 모르므로 determinate progress를 쓰지 않고,
  상태 문구가 진행 사실을 전한다 — [Loading](../patterns/loading.md)의 「완료 시간을 모름」 갈래다.
- 설명이 `white-space: pre-line`이라 **문구의 개행이 그대로 읽힌다.** 문장을 개행으로 끊으면
  스크린 리더의 호흡도 함께 끊긴다.
- 액션이 전폭 세로 목록이므로 **탭 순서가 시각 순서와 같다.** 가로 배치에서 생기는 어긋남이 없다.
- 결과 처리 오류의 붉은 배너는 **색만으로 전달하지 않는다** — 문구가 오류 사유를 담는다. 실패
  화면에는 이 배너가 없고 **Meta list 행**이 사유(code · message · orderId)를 담는다.

#### Acceptance tests

1. 컬럼이 `520px`을 넘지 않고 가운데 정렬된다. 컬럼 자체에 면·테두리가 없다.
2. 부품 사이 간격이 전부 `24px` 하나다.
3. 처리 중에는 컬럼이 위에서 밀리지 않고 카드 안 세로 중앙에 온다.
4. 메타 행의 마지막 구분선이 없다.
5. `dt`와 `dd`의 렌더 행간이 **같다**(각 21px).
6. 액션 버튼이 전폭이라 세로로 쌓인다.
7. 900px에서 메타 행이 세로로 접히고 `dd`가 좌측 정렬된다.

#### Pre-implementation blockers

- **900px 경계를 승인할 것인가.** 셸 경계와 다른 값이라 responsive matrix에 별도 축으로 올릴지
  이 화면 전용 예외로 둘지 정해야 한다.
- **secondary 액션이 팔레트 잉크를 쓰는 것을 계약으로 둘 것인가.** 시맨틱으로 바꾸면 한 테마에서
  면이 사라지므로 값 그대로 옮기되 이유를 남겨야 한다.

#### 승격 조건

- 위 두 blocker가 닫힌다.
- 컬럼 폭 · 세로 간격 · 상단 오프셋이 semantic token으로 선다.
- 그 전까지 이 문서의 값은 **제품 인용**이며 DS 계약이 아니다.

## Route Boundary

- Source: design/patterns/route-boundary.md
- Maturity: experimental

### Route Boundary

라우트가 실패했을 때 나오는 화면이다 — **404** · **오류** · **최후 경계** 셋.

**셋 중 하나는 디자인 시스템을 쓸 수 없다.** 최후 경계는 루트 레이아웃 자체가 실패했을 때 뜨므로
토큰도 i18n도 전역 CSS도 없다. 그것을 「토큰을 쓰도록 고치는」 것은 **그 화면을 못 쓰게 만드는
일**이다.

값은 배포본 인용이며 아직 DS 토큰이 아니다. 간격 환산 기준은 제품의 `--spacing: 2px`다.

#### 세 갈래

| 화면 | 언제 | 디자인 시스템 |
| --- | --- | --- |
| 404 | 라우트를 못 찾음 | **쓴다** — 토큰 · 타입 클래스 · 공용 Button |
| 오류 | 라우트 안에서 던짐 | **쓴다** — 404와 같은 뼈대 |
| 최후 경계 | **루트 레이아웃이 실패** | **못 쓴다** — 인라인 스타일 · 한국어 고정 |

**앞의 둘은 같은 뼈대를 쓰는데 공용 컴포넌트가 아니라 복제다.** 두 파일이 `ROOT` · `CONTENT` ·
`TITLE` · `DESCRIPTION` · `PAGE_CTA` 다섯 상수를 각자 자기 파일에 적는다. 값이 지금은 같지만
한쪽만 고치면 갈린다.

#### Layout contract (404 · 오류)

| 축 | 값 |
| --- | --- |
| 루트 | `min-height: 100svh` · `flex column` · 가로·세로 가운데 |
| 루트 패딩 | `24px 20px 32px` · **≤719px 좌우 `16px`** |
| 루트 면 · 전경 | `var(--background)` · `var(--foreground)` |
| 콘텐츠 폭 | `min(100%, 440px)` |
| 콘텐츠 배치 | `flex column` · 가운데 · `text-align: center` · `gap: 12px` |
| 제목 | `type-heading-36-medium` · `var(--foreground)` |
| 설명 | `type-body-16-regular` · `max-width: 36ch` · `white-space: pre-line` |
| 설명 전경 (다크) | `rgb(var(--gray-000-rgb) / 62%)` |
| 설명 전경 (라이트) | `rgb(var(--gray-000-rgb) / 58%)` |
| CTA 여백 | `margin-top: 12px` |

**`--background` / `--foreground`는 LOUIS에 이름이 없다.** 제품에서 `--gray-900` / `--gray-000`의
별칭이며, 셸 계열이 쓰는 `--app-page-bg`와 **다른 변수**다. 라우트 경계는 셸 밖이므로 셸 배경을
쓰지 않는다.

**설명이 `pre-line`이다.** 문구에 든 개행이 렌더에 그대로 나온다 — 한 줄로 합치면 화면이 달라진다.
`!`가 붙어 있는데, 랜딩의 레이어 밖 규칙이 `text-wrap` 단축으로 `white-space`를 함께 덮기 때문이다.

**CTA는 공용 Button(primary)이고 이 화면은 간격만 갖는다.** 색·높이·곡률·그림자는 Button이
소유한다. 자체 배경을 가진 클래스를 같이 주면 명시도가 같아 파랑이 덮인다.

**오류 화면에만 링크용 설명 변형이 하나 더 있다.** 값은 같고 `!`만 더 붙는다.

#### 최후 경계 — 토큰을 쓸 수 없다

루트 레이아웃이 실패한 뒤라 **전역 CSS도 i18n도 로드되지 않았다.** 그래서 자체 완결 인라인
스타일로만 그린다.

| 축 | 값 | 왜 여기만 다른가 |
| --- | --- | --- |
| 높이 | `100vh` | `svh`를 쓰려면 CSS가 필요하다 |
| 면 · 전경 | `#0a0a0a` · `#ededed` | 토큰이 없다 |
| 설명 전경 | `#a1a1a1` | 같음 |
| 폰트 | 시스템 스택 | 웹폰트가 로드되지 않았다 |
| 콘텐츠 폭 | `420px` | 앞의 둘(`440px`)과 다르다 |
| 패딩 | `24px` | |
| 제목 | `24px` · `600` | 타입 클래스가 없다 |
| 설명 | `15px` · `line-height 1.6` | 스케일 밖 값이다 |
| 버튼 | `10px 24px` · 곡률 `8px` · 면 `#ededed` · 글자 `#0a0a0a` | 공용 Button을 못 쓴다 |
| 언어 | **한국어 고정** | i18n이 없다 |

**이 값들을 토큰으로 바꾸지 마라.** 토큰을 참조하는 순간 이 화면은 자기가 막으려던 실패에 함께
휩쓸린다. **디자인 시스템이 닿지 않는 자리가 있다는 사실 자체가 계약이다.**

다만 **값이 앞의 둘과 어긋나 있다** — 폭 420 대 440, 제목 24px 대 heading-36, 설명 15px은 스케일
밖이다. 시스템을 못 쓰는 것과 값을 다르게 두는 것은 별개이므로, 인라인이더라도 **해결값을
맞추는 것**은 가능하다. 판정이 필요하다.

#### Accessibility

- 세 화면 모두 제목이 `<h1>`이고 페이지에 하나다.
- CTA가 `<button type="button">`이며 404는 홈 이동, 오류는 재시도다 — **되돌릴 길이 항상 하나 있다.**
- 최후 경계는 `<html lang="ko">`로 **언어가 고정된다.** 영어 사용자에게도 한국어가 나온다 —
  i18n을 못 쓰는 자리라 현재로선 대안이 없다.
- 설명이 `text-align: center`다. 긴 문구도 가운데 정렬된다.

#### Acceptance tests

1. 404와 오류가 같은 뼈대를 그린다 — 폭 440px · 간격 12px · 제목 heading-36-medium.
2. 설명의 개행이 렌더에 나타난다(`pre-line`).
3. 설명 전경이 테마에 따라 62% ↔ 58%로 갈린다.
4. CTA가 공용 Button primary이고 이 화면은 위 여백만 준다.
5. ≤719px에서 좌우 패딩이 20px → 16px로 줄어든다.
6. **최후 경계가 토큰을 하나도 참조하지 않는다** — 전역 CSS 없이 렌더된다.

#### Pre-implementation blockers

- **404와 오류의 복제를 공용으로 합칠 것인가.** 다섯 상수를 두 파일이 각자 적는다.
  합치는 것은 제품 변경이다.
- **최후 경계의 해결값을 앞의 둘과 맞출 것인가.** 폭 420 → 440, 제목 24px → heading-36의 해결값
  등. 인라인이라도 값은 맞출 수 있다.
- **`--background` / `--foreground`를 LOUIS 이름으로 세울 것인가.** 셸의 `--app-page-bg`와 다른
  축이고 현재 LOUIS에 대응이 없다.

#### 승격 조건

- 위 세 blocker가 닫힌다.
- 콘텐츠 폭 · 간격 · 설명 전경이 semantic token으로 선다.
- 그 전까지 이 문서의 값은 **제품 인용**이며 DS 계약이 아니다.

## Project Grid

- Source: design/patterns/project-grid.md
- Maturity: experimental

### Project Grid

Project Grid는 archive home, NodeCanvas hub, Video Editor history, Highlight history처럼 프로젝트를
탐색하는 공용 패턴이다. 핵심 계약은 **main content에 실제로 생긴 공간만큼 열 수가 늘고 줄어든다**는
것이다. 데스크톱 홈을 임의의 3열로 고정하지 않는다.

#### Use when

- 동일한 중요도의 프로젝트를 썸네일 중심으로 탐색할 때
- 프로젝트 종류가 달라도 open, rename, delete 같은 공통 동작을 제공할 때
- 최근 항목 한 행 또는 전체 archive 여러 행을 보여줄 때

순서 비교가 핵심인 표, 작은 텍스트 레코드, 타임라인 결과에는 Data Table 또는 List 패턴을 사용한다.

#### Anatomy

```text
Project section
├─ Section header
│  ├─ Label
│  ├─ Optional count
│  └─ Primary or overflow action
├─ State region
│  ├─ Loading / error / empty
│  └─ Grid
│     └─ Project card
│        ├─ Primary open action
│        │  ├─ Preview
│        │  ├─ Type / status
│        │  ├─ Title
│        │  └─ Updated time
│        └─ Overflow menu trigger
└─ Pagination or load-more sentinel when needed
```

카드 전체를 클릭 가능하게 보이게 하면서 focus 불가능한 `<article onClick>`로 구현하지 않는다. open은
명시적인 link 또는 button이 소유하고, overflow menu는 그 안에 중첩하지 않은 형제 컨트롤이어야 한다.

#### Layout contract

##### Column behavior

- Grid는 shell content box 안의 가용 폭을 모두 사용한다.
- 열 수는 component container에서 계산하며 sidebar의 expanded/collapsed 변화에도 다시 계산한다.
- 같은 상태에서 카드는 동일한 column track을 사용하고, 마지막 행이 덜 차더라도 앞선 카드 폭을 임의로
  늘리지 않는다.
- 카드가 승인된 최소 사용 폭보다 작아지기 전에 열 수를 줄인다. 최소 폭은 card primitive와 함께
  token으로 승인하며 이 문서에서 새 literal을 만들지 않는다.
- extra-wide에서 열 수를 늘려 정보 밀도를 유지한다. max-width로 전체 grid를 3열 폭에 가두지 않는다.
- gap은 공용 grid gap token을 사용하고 열 수가 달라져도 동일한 rhythm을 유지한다.

##### Migration compatibility

아래 결과는 승인된 migration compatibility profile이다. 구현은 container 기반으로 바꾸되,
기준 viewport와 기본 App Shell 상태에서 아래 결과를 유지한다.

| Current viewport | Compatibility result |
| ---------------- | -------------------- |
| `≤719px`         | 2열                  |
| `720–1199px`     | 3열                  |
| `1200–1799px`    | 4열                  |
| `≥1800px`        | 5열                  |

profile의 추출 provenance는 [`KP-GRID-001`](../../migration/product-baseline.md)에 있다.
wide/extra-wide에서 3열만 보이면 실패다.

Container 기반 구현에서는 viewport가 경계 안에 있어도 expanded sidebar, inspector, split pane 등으로
실제 container가 좁으면 열 수를 줄일 수 있다. 반대로 sidebar가 접혀 유효 폭이 늘면 같은 viewport에서
열 수가 늘 수 있다. 어떤 경우에도 카드가 겹치거나 horizontal scroll을 만들면 안 된다.

##### Home one-row variant

- archive home의 “최근 작업한 프로젝트”는 한 행만 보여준다.
- 로드할 항목 수는 **현재 실제 열 수**와 같아야 한다.
- resize로 열 수가 늘면 기존 카드 순서와 화면을 유지한 채 부족한 항목만 채운다. 전체 grid를 빈 상태로
  되돌리거나 순서를 흔들지 않는다.
- 열 수가 줄면 숨겨진 항목을 삭제한 것으로 취급하지 않는다. “전체 보기” 또는 archive route에서 계속
  접근 가능해야 한다.
- SSR 결과와 hydration 후 열 수가 달라도 layout shift를 최소화하고 중복 요청이 프로젝트 순서를 바꾸지
  않아야 한다.

한 행 소비처는 실제 열 수를 request limit과 동기화한다. resize에서는 기존 카드와 순서를 유지하며
부족분만 채우고 blank/flicker를 만들지 않는다.

##### Archive variant

- 전체 archive는 여러 행을 허용하고 pagination 또는 incremental loading을 사용한다.
- 새 데이터를 붙일 때 기존 DOM 순서와 focus를 유지한다.
- 정렬 기준은 API와 UI가 같은 필드를 사용해야 한다. rename/update 후 화면 순서와 상대 시간이 서버
  정렬과 달라지지 않게 한다.
- loading sentinel은 마지막 카드와 같은 grid cell인 척하지 않고 상태 region으로 노출한다.

#### Card behavior

##### Primary action

- preview, title, metadata를 포함하는 하나의 명확한 open target을 제공한다.
- Enter로 열 수 있어야 하며 새 탭 열기 같은 브라우저 link 동작이 필요한 경우 실제 link를 사용한다.
- hover, focus-visible, pressed 상태는 같은 geometry를 사용하고 색만으로 상태를 구분하지 않는다.
- preview 비율은 현재 square card를 migration compatibility로 유지한다. 다른 비율은 card variant 결정과
  썸네일 생성 계약을 함께 바꿀 때만 추가한다.

##### Overflow menu

- menu trigger는 pointer, touch, keyboard에서 항상 도달 가능해야 한다. hover에서만 나타나더라도
  `focus-within`, coarse pointer에서는 보인다.
- trigger는 카드 open action을 실행하지 않도록 event와 DOM ownership을 분리한다.
- menu는 grid/card overflow에 잘리지 않아야 하며 floating layer 또는 승인된 overlay root를 사용한다.
- `aria-haspopup`, `aria-expanded`, menu name을 제공하고 Arrow keys, Home/End, Escape, focus return을
  지원한다.
- rename/delete 뒤 focus를 다음 논리 카드 또는 section heading으로 이동한다.

##### Preview and metadata

- 콘텐츠 이미지에는 프로젝트를 구분할 수 있는 대체 텍스트를 제공하거나, 같은 link 안의 제목이 이름을
  제공하면 preview 이미지는 장식으로 숨긴다.
- title과 status를 영상 위에 올릴 때 썸네일 톤에만 의존하지 않고 모든 테마/이미지에서 읽을 수 있는
  overlay recipe를 사용한다.
- type, failure, processing 상태는 색뿐 아니라 label로 전달한다.
- 상대 시각은 locale에 맞추고 보조 기술이 이해할 수 있는 완전한 날짜를 함께 제공한다.

#### States

| State               | Contract                                                                              |
| ------------------- | ------------------------------------------------------------------------------------- |
| Initial loading     | 예상 grid 구조를 보존하는 skeleton 또는 구체적인 loading status를 제공한다            |
| Incremental loading | 기존 카드를 제거하지 않고 section에 `aria-busy`를 설정한다                            |
| Empty               | 무엇이 비었는지와 가능한 다음 행동을 제공한다                                         |
| Error               | empty와 구분하고 재시도 또는 복구 행동을 제공한다                                     |
| Rename              | title 위치에서 편집하되 입력 label, Enter/Escape, validation, focus return을 제공한다 |
| Delete pending      | 대상 이름과 영향을 확인하고 성공 전 카드를 제거하지 않는다                            |
| Processing project  | progress/status label을 유지하고 open 가능 여부를 명시한다                            |

로딩 표현은 [Loading](../patterns/loading.md), 버튼과 focus 기준은
[Inclusive Design](../foundations/inclusive-design.md)을 따른다.

**Initial loading의 두 갈래 중 제품은 status 쪽을 골랐다 (2026-08-30 실측).** 위 표는 skeleton과
"구체적인 loading status"를 나란히 허용하는데, 제품 소비처는 어느 쪽도 grid 구조를 세우지 않고
가운데 정렬한 쉬머 낱말 하나를 쓴다 — 첫 로드는 `AppHomeScene.tsx`의 `archiveLoadingState`
섹션(`aria-live="polite"`) 안에 `role="status"`와 `aria-label`을 단 `type-heading-28-medium` 낱말
하나이고, 더 불러오기는 `NodeCanvasHomeScene.tsx`의 `ARCHIVE_LOADING_MORE_TEXT`가 같은
그라디언트 sweep을 옮겨 적은 둘째 벌이다. 계약 위반은 아니지만 **Loading 패턴의 선택 기준은
"구조가 정해진 카드·목록의 첫 로드 → Skeleton"이라 방향이 반대다.** 어느 쪽을 정본으로 삼을지는
아직 판정되지 않았고, 정해지기 전에는 Figma의 이 자리를 옮기지 않는다.

#### Responsive behavior

| Mode        | Section header                                          | Grid                                      | Card actions                               |
| ----------- | ------------------------------------------------------- | ----------------------------------------- | ------------------------------------------ |
| Regular     | label/count와 primary action을 한 행에 둔다             | container 폭에 따라 3–5열 호환 결과       | hover와 focus에서 overflow 표시            |
| Constrained | 긴 label과 action이 충돌하면 action을 menu화하거나 wrap | usable card width를 먼저 보장하고 열 감소 | 필수 액션은 focus/touch에서 항상 표시      |
| Compact     | label과 action이 필요하면 wrap 가능                     | 현재 호환 결과 2열                        | touch target을 카드 모서리와 안전하게 분리 |

열 수와 데이터 요청 수는 같은 column calculation 결과를 공유한다. CSS는 4열인데 JS가 3개만 요청하는
식으로 서로 다른 breakpoint 표를 복제하지 않는다.

#### Accessibility

- section heading과 grid를 `aria-labelledby`로 연결한다.
- 단순 CSS grid는 별도 `role="grid"`를 붙이지 않는다. 복합 grid keyboard model을 구현하지 않는 한
  native link/button 목록으로 둔다.
- DOM과 시각적 프로젝트 순서를 일치시킨다.
- 모든 card open action과 menu trigger에 명확한 focus-visible indicator를 제공한다.
- drag/reorder를 도입하면 keyboard 대체 동작과 현재 위치 안내를 함께 제공한다.
- reduced-motion에서 staggered card entrance와 scale transition을 제거해도 콘텐츠가 즉시 보여야 한다.

#### Extraction baseline

Home, Video Editor history, Highlight history/clip에서 2/3/4/5열과 한 행 요청 개수를 사용한 결과는
migration compatibility로 보존한다. 비규범 provenance는
[`KP-GRID-001`](../../migration/product-baseline.md)에 있다.

Scene별 markup, viewport-only query, keyboard로 열리지 않는 card, local overflow menu와 불안정한
refetch 순서는 공용 recipe로 가져오지 않는다.

#### Pre-implementation blockers

- P2 local RC에 `layout-project-card-minimum`과 `layout-project-grid-gap` 토큰은 있다. 이를 소비하는 container
  기반 공용 grid recipe와 실제 카드 content 실측은 아직 없다.
- **`auto-fill` 환산과 migration compatibility profile이 아직 같은 답을 내지 않는다.** 240 / 6으로는
  720px에서 2열(profile 3), 1800px에서 7열(profile 5)이다. 하나의 카드 최소 폭으로는 양쪽을 동시에
  만족시킬 수 없으므로, profile을 유지한 채 container 기반으로 가려면 열 수 상한을 함께 두는 등
  공식 자체를 바꿔야 한다. 그 판정 전까지 정본은 profile이다.
- link/button primary action과 overflow overlay test가 없다.
- loading/error/empty state와 resize/refetch 안정성 contract가 구현되지 않았다.
- Highlight history/clip variant의 visual regression이 없다.

#### Acceptance tests

- Home recent, Video Editor history, Highlight history/clip 소비처가 네 기준 viewport 구간에서 2/3/4/5열
  호환 결과를 내며 wide 화면이 3열에 고정되지 않는다.
- 각 기준에서 sidebar expanded/collapsed를 전환해 grid가 실제 content box에 맞게 재계산되고 겹침·가로
  scroll이 없다.
- archive home은 정확히 한 행을 채우고 resize 중 기존 카드가 사라지거나 순서가 바뀌지 않는다.
- keyboard만으로 모든 카드를 열고 overflow menu의 모든 항목을 실행한 뒤 focus가 복원된다.
- touch/coarse pointer에서 overflow trigger를 hover 없이 찾고 누를 수 있다.
- empty, initial loading, incremental loading, request failure를 시각·접근성 트리에서 구분한다.
- 200% 확대와 KO/EN/JA 긴 제목에서 open target과 menu가 겹치지 않는다.
- light/dark, 밝고 어두운 썸네일, reduced-motion에서 title/status/focus가 읽힌다.

#### 구현 (2026-08-18)

공용 recipe는 `.louis-project-grid` 하나다.

```css
display: grid;
gap: var(--louis-layout-project-grid-gap);
grid-template-columns: repeat(
  auto-fill,
  minmax(min(var(--louis-layout-project-card-minimum), 100%), 1fr)
);
```

**`auto-fill`이 grid 자신의 content box로 열 수를 계산한다.** 그래서 사이드바가 접혀 유효 폭이
늘면 같은 viewport에서 열이 늘고, 좁은 패널 안에 놓이면 준다 — media query로는 그 둘을 구분할 수
없다. 이 recipe의 열 수는 `floor((W + gap) / (최소 + gap))`이다.

**그 환산은 위의 compatibility profile을 재현하지 못한다 — 정본은 profile 쪽이다.** 오늘의
토큰 값(`layout-project-card-minimum` 240px · `layout-project-grid-gap` 4px,
`packages/tokens/generated/tokens.css:478-479`)을 넣으면 한 열이 244px씩 들어가므로, 폭 720px에서
`floor(724 / 244)` = 2열이고 profile은 3열, 폭 1800px에서 `floor(1804 / 244)` = 7열이고 profile은
5열이다. 두 축이 맞는 곳은 1200px 구간(4열)뿐이다. 최소 폭을 되튜닝해도 풀리지 않는다 —
720px에서 3열이 나오려면 `최소 + gap`이 242px 이하여야 하고 1800px에서 5열이 나오려면 302px
이상이어야 해서, 하나의 최소 폭이 동시에 만족시킬 수 없다.

gap 을 4px 에서 6px 로 올려도 이 엇갈림은 그대로다 — 네 구간의 답(2·4·7열과 profile 3·4·5)이
바뀌지 않는다. **gap 은 이 blocker 의 원인이 아니다.**

profile은 승인된 값이고 제품이 그대로 구현하고 있다 — 제품 `appHomeSceneStyles.ts`의
`archiveGrid`는 `repeat(2, 1fr)`에 `min-[720px]` 3열 · `min-[1200px]` 4열 · `min-[1800px]` 5열을
얹은 고정 media query다. 그러므로 위 CSS는 **아직 profile을 만족하지 않는 구현안**이고, 둘을
잇는 값은 미정이다. 위의 Pre-implementation blockers에 적어 두었다.

**브라우저 테스트는 이 어긋남을 볼 수 없다.** `packages/react/test/project-grid.browser.test.tsx`는
대조할 폭을 `want * 최소 + (want - 1) * gap`으로 **같은 토큰에서 유도**한다. 그래서 그 표는
공식이 자기 자신과 일관된다는 것만 증명하고, profile의 720 / 1200 / 1800을 한 번도 넣어 보지
않는다. 이 문단이 고쳐지기 전까지 그 테스트의 초록은 환산이 맞다는 증거가 아니었다.

**`min(최소, 100%)`가 1열 fallback을 만든다.** 그것이 없으면 container가 카드 최소 폭보다 좁을 때
track이 container를 넘어 가로 스크롤이 생긴다.

이 규칙이 **`layout-project-card-minimum`의 첫 CSS 소비처**다. 그 전까지 그 토큰은 소비처가
0이었고 gap registry가 "존재하지 않는 알고리즘을 기술하는 토큰"으로 분류해 두었다.

##### Acceptance tests

1. 열 수가 container 폭에서 유도된다 — 1·2·3·4·5열이 각각 그 폭에서 나온다.
2. **viewport를 바꾸지 않고 container만 줄여도** 열이 준다.
3. 최소 폭보다 좁으면 1열로 떨어지고 **가로 스크롤이 없다.**
4. 마지막 행이 덜 차도 모든 카드의 폭이 같다.
5. gap이 공용 토큰이고 열 수가 달라져도 같다.

##### 남은 것

한 행 소비처의 request limit 동기화와 resize 시 항목 보존은 **소비 제품의 데이터 흐름**이라
`DS-P5-003`이 소유한다. 이 패턴이 소유하는 것은 열 수 계산과 fallback까지다.

## Editor Workspace

- Source: design/patterns/editor-workspace.md
- Maturity: experimental

### Editor Workspace

Editor Workspace는 preview, assets, properties, timeline처럼 여러 작업 pane이 동시에 필요한 편집 화면의
구조 계약이다. **route workspace와 modal editor를 같은 것으로 취급하지 않는 것**이 첫 규칙이다.

mode는 API와 DOM semantics에서 명시적으로 분리하며 portal target이나 ref timing으로 추론하지 않는다.

#### Modes

| Mode                     | 예                                          | 소유 영역                                          | Modal semantics                                                                 |
| ------------------------ | ------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------- |
| Route / docked workspace | 독립 editor project, highlight short editor | App Shell이 준 workspace host                      | 아니다. route main content이며 backdrop, `aria-modal`, focus trap을 쓰지 않는다 |
| Modal editor             | canvas에서 임시 editor 열기                 | viewport의 승인된 modal layer                      | 맞다. 뒤 UI를 inert 처리하고 focus를 가둔다                                     |
| Compact route workspace  | 작은 viewport의 project editor              | App Shell main 영역 전체, navigation은 닫힌 drawer | route다. 화면을 채워도 dialog로 노출하지 않는다                                 |

Mode를 `portalContainer`의 null 여부나 우연한 ref timing으로 추론하지 않는다. public API는
`mode="route" | "modal"`처럼 의도를 직접 표현해야 하며 잘못된 mode는 개발 단계에서 실패해야 한다.

#### Anatomy

```text
App Shell                         ← route mode에서만
├─ Navigation rail / drawer       ← App Shell 소유
├─ Top chrome                     ← back, title, save/export, profile
└─ Workspace host
   └─ Editor workspace
      ├─ Assets pane
      ├─ Preview pane
      ├─ Properties / inspector pane
      ├─ Timeline pane
      ├─ Pane dividers / collapse controls
      └─ Local overlay root

Global overlay root               ← profile, command palette, modal confirm
```

Route mode에서 workspace host는 top chrome 아래 남은 surface를 채운다. Editor는 host 밖의 sidebar 공간을
계산하지 않는다.

#### Ownership boundaries

##### App Shell owns

- sidebar expanded/collapsed/drawer state와 main offset
- viewport height, safe area, route top chrome
- breadcrumb/back, profile, command palette 같은 global chrome
- global non-modal과 modal overlay root
- immersive route 진입 시 임시 sidebar collapse와 이탈 시 복원

##### Editor owns

- assets, preview, inspector, timeline의 배치와 크기 상태
- pane resize/collapse, selection, playback, timeline keyboard interaction
- workspace host 안의 tooltip, menu, crop/guide overlay
- dirty/save/export 상태를 top chrome action slot에 제공하는 것

##### Editor must not own

- `100vw - sidebar width` 같은 shell geometry
- body에 직접 올린 임의 z-index 경쟁
- route mode의 backdrop, page-level focus trap, click-outside close
- profile popover나 sidebar pointer handling

#### Route workspace contract

- workspace root는 host를 기준으로 `inset: 0` 또는 flex fill하며 `min-width: 0`, `min-height: 0`을 가진다.
- regular/constrained mode에서 root는 host-relative다. viewport `position: fixed`로 sidebar reserve를 무시하지
  않는다.
- App Shell sidebar가 펼쳐지거나 접히면 host rectangle이 바뀌고 workspace는 그 안에서 reflow한다.
- immersive editor 진입 시 sidebar를 임시 collapse할 수 있다. 이 상태는 사용자
  preference를 덮어쓰지 않고 이탈 시 복원한다.
- 사용자가 편집 중 sidebar를 직접 펼치면 workspace가 밀려나거나 재배치되어야 한다. sidebar가 editor
  assets pane 위에 겹치면 실패다.
- 내부 editor header의 title/action을 top chrome으로 옮겼다면 원래 header는 중복 렌더하지 않는다. action
  portal 대상이 첫 render에 없더라도 두 벌의 저장/완료 버튼이 잠시 보이면 안 된다.
- editor scroll은 workspace 내부 pane이 소유하고 body/main page scroll과 경쟁하지 않는다.

#### Modal editor contract

- 승인된 global modal root에 렌더하고 route content, navigation, global non-modal을 inert 처리한다.
- dialog name/description, initial focus, Tab containment, Escape, close 후 trigger focus 복원을 제공한다.
- backdrop activation은 drag 종료나 pointer capture와 충돌하지 않아야 한다.
- modal mode의 full-viewport stacking은 route mode에 전달되지 않는다.
- nested confirm/crop/help overlay는 가장 최근에 열린 layer부터 Escape로 닫힌다.
- 저장하지 않은 변경이 있으면 close request와 discard confirm을 분리한다.

#### Pane layout

##### Regular

- 상단 작업 행은 assets, preview, inspector를 두고 timeline은 하단 작업 행을 소유한다.
- preview가 핵심 pane이며 보조 pane 최소값 때문에 0 이하로 압축되지 않는다.
- pane width/height는 resize 가능한 state와 승인된 범위에서 관리한다. CSS literal과 component state가
  서로 다른 기본값을 갖지 않는다.
- divider는 pointer drag 외에 keyboard 조절과 reset을 제공한다.
- collapsed pane은 focus 순서와 접근성 트리에서 제거되고 명시적인 restore control을 남긴다.

기본 recipe는 assets, divider, preview, divider, properties와 하단 timeline 관계를 사용한다. pane
폭과 timeline 높이는 승인된 semantic token/state에서 오며 임의 fallback 숫자를 token으로 승격하지
않는다.

##### Constrained

- host 폭이 모든 pane을 안전하게 담지 못하면 낮은 우선순위 pane부터 collapse 또는 drawer/tab로 옮긴다.
- App Shell을 포함한 문서 전체 horizontal scroll로 작업 공간을 숨기지 않는다.
- preview, playback, timeline, save/export는 계속 도달 가능해야 한다.
- breakpoint는 viewport가 아니라 workspace host의 pane 최소 요구량에서 결정한다.

constrained recipe는 compact 전환 전에도 전역 최소폭과 가로 scroll에 의존하지 않아야 한다.

##### Compact

- App Shell sidebar reserve는 0이고 navigation drawer는 기본 닫힘이다.
- pane은 한 열의 단계형 구조, tabs, sheets 중 하나로 표현한다.
- preview, timeline, inspector뿐 아니라 **assets에도 명시적인 진입점**이 있어야 한다.
- 숨은 implicit CSS grid track에 assets가 우연히 배치되는 구현을 허용하지 않는다.
- 완료/저장/뒤로가기 같은 route action은 safe area 안에 유지하고 가상 키보드에도 가려지지 않는다.
- 높이가 짧으면 pane의 고정 최소 높이를 모두 유지하려 하지 말고 active pane에 scroll을 부여한다.

compact recipe가 assets 진입점을 생략하면 문서 순서나 숨은 implicit grid track에 우연히 배치하지 않고
검증 단계에서 실패한다.

#### Responsive matrix

| Mode              | Shell navigation                                 | Pane presentation                                    | Overlay scope                                                |
| ----------------- | ------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------ |
| Regular route     | 임시 collapsed persistent rail, 사용자 전환 가능 | assets + preview + inspector / timeline              | local overlay는 host, global overlay는 shell root            |
| Constrained route | rail이 차지한 뒤 host 기준                       | 보조 pane collapse·tab·drawer, preview/timeline 유지 | local overlay가 host 밖 sidebar를 덮지 않음                  |
| Compact route     | reserve 0, 닫힌 overlay drawer                   | 명시적인 single-column/step structure                | editor는 main 영역을 채우고 shell drawer는 별도 global layer |
| Modal             | 배경 navigation inert                            | viewport 안에서 regular/compact editor layout 선택   | modal root가 소유, nested modal은 overlay service 사용       |

compact 호환 경계는 [Responsive Layout](../foundations/responsive-layout.md)에 기록한다. container 기반
전환은 위 기능 결과를 우선한다.

#### Canvas node side controls

캔버스 노드 카드는 좌·우 **바깥**에 28px 정사각 컨트롤 레일을 세운다. 제품은 이 레일을 카드 안이 아니라
카드 패딩 박스 바깥에서 계산하고, 값은 전역 변수 한 벌에서만 가져온다. **컨트롤 자리를 카드 폭에
포함시켜 계산하면 카드와 레일이 함께 어긋난다.**

| CSS variable | 해결값 | 지배하는 자리 |
| --- | --- | --- |
| `--node-side-handle-size` | `28px` | 사이드 버튼·핸들 한 변 — `globals.css:483` |
| `--node-side-handle-radius` | `8px` | 그 크롬의 모서리 — `globals.css:484` |
| `--node-side-gap` | `10px` | 카드 패딩 박스 ↔ 컨트롤 열 **수평** 간격 — `globals.css:492` |
| `--node-side-stack-gap` | `8px` | 같은 열 컨트롤끼리 **세로** 간격 — `globals.css:494` |
| `--node-side-ctrl` | `var(--node-side-handle-size, 28px)` | 레일 계산이 참조하는 한 변 — `globals.css:495` |
| `--node-side-leading-offset` | `calc(gap + ctrl)` = **38px** | 카드 왼쪽 테두리 ↔ 좌 레일 바깥선 — `globals.css:496` |
| `--node-handle-outbound-slot` | `calc(100% + gap)` | 우 출력 `left:`·좌 레일 `right:` 공통식 — `globals.css:497` |

규범 주석은 `globals.css:486-491`에 있다. 캔버스 셸이 같은 이름으로 덮어쓸 수 있게 열어 두었으나 현재
재정의하는 곳은 없다.

##### 레일 배치

- 좌 레일은 `left: calc(-1 * var(--node-side-leading-offset))`에 선다.
  `right: var(--node-handle-outbound-slot)`은 같은 자리의 다른 표기다.
- 우 출력 핸들은 `left: var(--node-handle-outbound-slot)`에 선다.
- 둘 다 `top: 50%` + `translateY(-50%)`로 카드 세로 중앙에 건다. 레일 컨테이너는 `z-[5]`다.
- 한 열에 컨트롤이 여럿이면 세로 간격은 gap(10px)이 아니라 stack-gap(8px)이다.
  **n개 스택의 총높이 = n × 28 + (n − 1) × 8** — 4개면 136px.

수평 간격과 세로 간격을 한 값으로 합치면 레일 길이가 스택 개수마다 틀린다. 코드에서 `38px`을 직접
적는 것도 틀린다 — 그것은 `gap + ctrl`의 현재 해이고, gap이 바뀌면 좌 레일만 밀린다. Figma처럼 변수를
바인딩할 수 없는 도구로 옮길 때만 해결값 38px을 쓰고 파생 관계를 함께 적는다.

##### Outset은 전역이 아니다

`--node-side-outset`은 전역 변수가 아니다. 노드 컴포넌트가 각자 로컬로 `0px`을 선언한다 —
`VideoNode.tsx` · `ImageNode.tsx` · `TextNode.tsx` · `TtsNode.tsx` · `BgmNode.tsx` 다섯이고, 그 밖의
노드(`EditNode.tsx` · `YoutubeNode.tsx` · `InstagramNode.tsx`)는 선언 없이 `var(--node-side-outset, 0px)`
폴백만 읽는다.

값이 `--node-side-leading-offset`(38px)으로 올라가는 것은 `[data-node-canvas-marketing]` 스코프
안에서뿐이고, **그 override를 가진 노드는 `VideoNode.tsx` · `ImageNode.tsx` · `TextNode.tsx` 셋뿐이다.**
`TtsNode.tsx` · `BgmNode.tsx`는 마케팅 스코프에서도 `0px`로 남는다. override가 걸린 노드에서는 같은
자리에서 정렬도 `center`에서 `stretch`로 바뀐다 — 마케팅 임베드는 좌우 크롬을 노드 박스 안에 포함하기
때문이다. 그래서 노드 바깥 박스 폭이 문맥마다 갈린다.

| 문맥 | outset | 카드 폭 | 바깥 박스 폭 |
| --- | ---: | ---: | ---: |
| 앱 에디터 캔버스 | `0px` | 400px | **400px** |
| 랜딩·마케팅 임베드 (video · image · text 노드) | `38px` | 400px | **476px** |

바깥 박스 폭 = `카드 폭 + 2 × outset`이다. 랜딩 쇼케이스 문서에서 노드의 `position.x`는 카드가 아니라
이 바깥 박스의 왼쪽을 가리킨다. 앱 값 400px로 랜딩 간격을 계산하면 노드마다 76px씩 밀린다.

**`--node-side-outset`을 전역 SSOT로 승격하지 않는다.** 올리는 순간 앱 캔버스가 랜딩 폭을 상속하고
카드가 컨트롤 자리만큼 안으로 밀린다.

##### 카드 외곽선의 SSOT는 카드가 아니라 셸이다

**노드 모듈은 자기 border를 선언하지 않는다.** 캔버스 셸이 후손 셀렉터로
`[data-node-chrome="wrap"]`에 두께와 색을 **일괄 공급**한다. 카드가 자기 border를 다시 선언하면
회귀다.

| 상태 | 값 |
| --- | --- |
| 비선택 · 다크 | `2px solid rgb(var(--palette-gray-600-rgb) / 100%)` = `#777d89` |
| 비선택 · 라이트 | `2px solid rgb(var(--palette-gray-000-rgb) / 100%)` = `#fafafa` |
| 선택 (양 테마) | `2px solid rgb(var(--node-selection-accent-rgb) / 86%)` |

**시맨틱이 아니라 팔레트를 직접 읽는다.** `--gray-600`이 아니라 `--palette-gray-600-rgb`다 —
시맨틱으로 옮기면 테마에서 뒤집혀 두 상태가 같은 색이 된다.

계약 넷이 코드 주석에 적혀 있다.

1. **두께는 셸이 공급한다.**
2. **선택은 색 전환만이다** — 성능을 위해 `box-shadow`를 더하지 않는다.
3. **선택 규칙은 정렬에 맡기지 않고 `!`로 승자를 고정한다** — 원본에서 라이트 규칙보다 뒤에 있었다.
4. **선택 시 타이틀 줄도 같은 액센트를 100%로 받는다.** 미디어 오버레이 헤더는 제외인데
   **현재 그 표식을 붙이는 곳이 없다** — 배선 전이다.

**반경도 셸이 준다.** `--node-outer-radius: 24px`이고 안쪽은 `--node-inner-radius: 22px`다 —
**외곽에서 border 2px를 뺀 값**이다. 두 값을 따로 정하면 border 안쪽 콘텐츠가 모서리에서 어긋난다.
내부 입력 상자는 `--node-input-radius: 16px`로 또 다르다.

##### 면에는 SSOT가 없다

**선은 셸이 한 곳에서 주는데 면은 그렇지 않다.** 노드 **여덟이 각자** 같은 두 줄을 자기
`NODE_WRAP` 상수에 인라인 복제한다.

| 테마 | 면 |
| --- | --- |
| 다크 | `rgb(var(--gray-800-rgb) / 100%)` |
| 라이트 | `rgb(var(--palette-gray-100-rgb) / 100%)` — 사이드바 램프 아래에서는 `#f8f8f9` |

**같은 카드에서 선은 팔레트를 읽고 면은 시맨틱(다크)과 팔레트(라이트)를 섞어 읽는다.** 셋을 한
규칙으로 통일하면 어느 한 테마가 틀린다.

**한쪽만 고치면 여덟 중 일곱이 남는다.** 면을 셸로 올리는 것은 제품 변경이므로 여기서 정하지
않고, 옮길 때는 **여덟이 같은 값이라는 사실**만 계약으로 쓴다.

선택 액센트는 채널마다 다르다. 일곱 채널의 값은
[DS-D-0010](../governance/decisions/DS-D-0010-token-coverage.md)의 선택 액센트 절이 소유한다.
**한 색으로 옮기면 일곱 중 여섯이 틀린다.**

근거: `components/scenes/create/node-canvas-v2/index.tsx:353-365` ·
`globals.css:655`(다크 램프 `--gray-800-rgb`)·`:56`(`--palette-gray-800-rgb`) ·
`:48`(라이트 `--palette-gray-100-rgb`)·`:30`(`--palette-gray-100`).

##### 같은 숫자가 CSS 밖에 두 벌 더 있다

기하 값이 CSS 변수 한 벌로 끝나지 않는다. **TypeScript 상수가 같은 숫자를 다시 적고, 세 번째 벌이
썸네일 레이아웃에 또 있다.** 셋은 **수기 동기화 계약**이라 한쪽만 고치면 화면이 어긋난다.

| 상수 | 값 | CSS 대응 |
| --- | ---: | --- |
| `NODE_SIDE_GAP_PX` | 10 | `--node-side-gap` |
| `NODE_SIDE_STACK_GAP_PX` | 8 | `--node-side-stack-gap` |
| `NODE_SIDE_CONTROL_PX` | 28 | `--node-side-handle-size` |
| `NODE_SIDE_OUTSET_PX` | 38 | `--node-side-leading-offset` |
| `NODE_FLOW_OUTER_WIDTH_PX` | 476 | 카드 400 + 2 × 38 |

근거는 `components/scenes/create/node-canvas-v2/constants.ts:23-32`이고, 세 번째 벌은
`node-canvas-v2/lib/archiveThumbnail/layout.ts:41-42`가 **토큰 참조 없이 자기 리터럴로** 다시 적는다.

**Figma로 옮길 때 `28 · 10 · 8 · 38 · 476`을 한 세트로 옮긴다.** 하나만 바꾸면 랜딩 쇼케이스 배치와
썸네일 렌더가 앱 화면과 갈린다.

##### 알려진 어긋남

**이 어긋남은 제품이 해소했다 — 토큰을 없애는 쪽으로.** 앞선 판은
`--node-handle-chrome-transition`(= `background 0.13s ease, color 0.13s ease, transform 0.1s ease`)이
이름과 달리 사이드 컨트롤 shell과 겹치지 않는다고 적고 「승격 전에 둘 중 어느 쪽이 계약인지 정한다」로
남겨 두었다. 배포본 `74a7303b`에 **그 토큰은 선언이 하나도 없다.** 지금은 전환을 토큰으로 두지
않는다는 것 자체가 규범이고, 제품 주석이 그것을 직접 적는다 — 「전환은 토큰이 아니라 소비처
유틸리티에 직접 적는다 — 셸은 `filter/color/border-color 0.13s ease`, 아이콘 스케일만
`transform 0.1s ease`」(`globals.css:429-430`).

**그래서 승격할 전환 토큰이 없다.** 사이드 컨트롤의 전환 사양은 소비처 유틸리티에서 읽는다.

핸들 shell/facet 2층 골격을 포함한 비규범 근거는
[`legacy-design-system.md` §6.9](../../migration/legacy-design-system.md)에 있다.

#### Overlay and portal contract

##### Local overlays

다음은 workspace host 또는 editor shell을 기준으로 위치한다.

- pane menu, tooltip, selection handles
- crop overlay와 composition guide
- timeline hover preview와 drag tooltip
- inspector option list가 host를 벗어날 필요가 없는 경우

local overlay는 sidebar/top chrome/profile popover보다 높은 viewport stacking context를 만들지 않는다.
host가 `overflow: hidden`이어도 떠 있는 menu가 필요하면 host 내부 local overlay root를 둔다.

##### Global overlays

다음만 App Shell overlay service로 승격한다.

- profile popover와 command palette
- plan gate, destructive confirm, unsaved-change confirm
- viewport 기준 positioning이 실제 요구인 floating UI

승격 시 layer semantics, focus ownership, close order를 선언한다. 단순히 clipping을 피하려고
`document.body`로 보내지 않는다.

##### Interaction guarantees

- global profile popover가 보이면 editor 위에서 pointer와 keyboard로 menu item을 선택할 수 있다.
- modal dialog가 열리면 profile popover와 local menu는 닫히거나 inert다.
- nested overlay에서 Escape는 topmost layer 하나만 닫는다.
- overlay close 후 focus는 editor selection을 파괴하지 않는 논리 trigger로 돌아간다.
- route editor와 modal editor의 z-index가 같은 selector나 상수로 섞이지 않는다.

#### Keyboard and accessibility

- route mode root에는 `role="dialog"`/`aria-modal`을 붙이지 않는다. `<main>` 또는 이름 있는 application
  region 안에 pane landmark를 제공한다.
- assets, preview, inspector, timeline은 heading 또는 `aria-label`로 구분한다.
- pane resize/collapse, timeline zoom, clip 이동·자르기에는 keyboard 대체 동작을 제공한다.
- Space 재생/정지는 text input, menu, dialog에서 동작하지 않게 scope를 관리한다.
- focus가 숨긴 pane이나 뒤 modal layer에 남지 않아야 한다.
- 처리 상태는 구체적인 `role="status"`/progress semantics를 제공하고 편집 가능한 영역 전체를 불필요하게
  막지 않는다.
- reduced-motion에서 shell open/close와 pane 이동은 즉시 전환하되 drag/selection 결과는 유지한다.
- 200% 확대와 KO/EN/JA 긴 action label에서도 save/export/back을 사용할 수 있어야 한다.

#### Extraction baseline

제품 구현의 host-scoped route workspace와 immersive route collapse/restore 결과는 보존하되,
Modal과 Workspace를 portal 유무로 분기한 API는 가져오지 않는다. compact assets 접근 누락,
body-portal floating UI, raw layer 숫자와 sidebar overlap 위험은 해결 대상이다.

비규범 provenance는 [`KP-EDITOR-001`](../../migration/product-baseline.md)에 있다.

#### 면 색 — 이 패턴은 토큰이 없어 제품을 그대로 인용한다 (2026-08-30)

에디터의 바닥과 패널 면은 **LOUIS 시맨틱으로 표현할 수 없다.** 값이 이렇다.

| | 라이트 | 다크 |
| --- | --- | --- |
| 워크스페이스 바닥 | `#f1f1f3` (`--palette-gray-100`) | `#313640` (`--palette-gray-800`) |
| 패널 넷 (assets · preview · properties · timeline) | `#e3e4e8` (`--palette-gray-200`) | `#171b22` (`--palette-gray-900`) |

**패널이 바닥보다 어둡다 — 두 테마 모두.** 일반 시맨틱 `bg-canvas`/`bg-surface` 는 그 반대를
전제한다(표면이 바닥 위로 뜬다). 그래서 그 둘을 갖다 붙이면 **밝기 관계가 통째로 뒤집힌다.**
`bg-surface` 의 값 자체는 그 뒤 움직였다 — 여기 `#313640` 이라 적혀 있던 다크 값은 회색 램프
재구성과 2026-09-09 의 다크 사다리 이동을 거쳐 지금 `palette-gray-850` `#21252d` 다(`bg-canvas`
(dark)는 `palette-gray-900` `#171b22`). **뒤집힘이라는 사실은 값과 무관하게 그대로다** — 넷이
함께 내려갔고 표면은 여전히 바닥 위로 뜬다. 위 표의 제품 hex 넷은 2026-08-30 실측 당시의
값이다.

Figma 변수를 전수 조회해 확인했다.

- 바닥 짝(`#f1f1f3` / `#313640`)을 가진 변수는 셋 있으나 전부 다른 역할 이름이다 —
  `color/bg-menu` · `color/table-header-surface` · `color/dropdown/surface-bg`. 이름이 참이어야
  한다는 [DS-D-0029](../governance/decisions/DS-D-0029-token-names-must-be-true.md) 때문에 쓸 수 없다.
- **패널 짝(`#e3e4e8` / `#171b22`)을 가진 변수는 하나도 없다.**

그래서 `Pattern · EditorWorkspace` 의 면은 변수 바인딩이 아니라 **제품 인용 리터럴**이고,
프레임 이름에 다크 짝을 적어 둔다. 보드가 라이트로 그려지므로 리터럴은 라이트 값이다.

**이 패턴을 `done` 으로 올리려면 선행 판정이 필요하다** — 에디터 바닥·패널에 semantic 두 개를
세울 것인가, 아니면 이 축을 영구히 제품 인용으로 둘 것인가. 세운다면 두 값이 램프를 타지 않는
고정 팔레트 조합이라 light/dark 두 mode 를 갖는 semantic 이어야 한다.

**제품을 시맨틱 쪽으로 뒤집는 선택은 하지 않았다.** 그것은 라이트·다크 양쪽에서 눈에 보이는
외형 변경이고, 이 문서 어디에도 「패널이 바닥 위로 떠야 한다」는 규범이 없다. 소유자 판정으로
남긴다(2026-08-30, 소유자가 「Figma 를 제품에 맞춘다」를 택했다).

#### Pre-implementation blockers

- route와 dialog를 명시적으로 분리한 workspace API가 없다.
- regular/constrained/compact pane recipe와 assets 대체 진입점이 없다.
- local/global overlay service와 Escape/focus ownership test가 없다.
- pane resize keyboard alternative와 responsive geometry regression이 없다.

#### Acceptance tests

##### Geometry

- regular route에서 sidebar expanded/collapsed/auto-collapsed 각각 navigation과 editor rectangle이 겹치지
  않는다.
- editor 진입 전 sidebar 상태가 이탈 후 복원되고, 편집 중 사용자 전환은 즉시 workspace를 reflow한다.
- compact route에서 sidebar reserve가 0이고 drawer가 닫힌 상태로 시작하며 assets, preview, timeline,
  inspector, save/export에 모두 도달한다.
- 짧은 viewport와 200% 확대에서 pane이 workspace 밖으로 밀려 완료 액션이 사라지지 않는다.
- body와 workspace가 동시에 가로/세로 scroll하지 않는다.

##### Overlay

- editor route에서 profile popover를 열고 pointer·keyboard로 설정/구독/언어/테마 항목을 선택한다.
- profile popover 위를 투명한 editor root가 가로채지 않는다.
- crop/help/local menu → global confirm 순서로 중첩하고 Escape가 topmost layer 하나씩 닫히는지 확인한다.
- modal editor를 열면 navigation과 route content가 inert이고 닫으면 원래 trigger로 focus가 돌아온다.
- route editor에는 backdrop click close나 modal focus trap이 적용되지 않는다.

##### Interaction and accessibility

- keyboard만으로 pane 이동, collapse/restore, resize 대체, playback, save/export를 완료한다.
- focus가 숨겨진 pane, 닫힌 menu, modal 뒤에 남지 않는다.
- processing, upload, render success/failure가 screen reader에 중복 없이 전달된다.
- light/dark, reduced-motion, KO/EN/JA에서 top chrome과 editor action이 중복되거나 잘리지 않는다.
