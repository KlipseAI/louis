#### 이 9개를 감싸는 크롬 — 루트 레이아웃뿐이다

라우트 그룹은 없고, 존재하는 `layout.tsx` 4개는 전부 `export const metadata` 뒤에 `return children` 만 한다. 따라서 인증 화면 위에 있는 것은 `app/layout.tsx` 두 겹이 전부다.

```

├─ PastDueBanner                    ← SITE_ROOT 의 형제, 앞에 놓인다
└─ SITE_ROOT    min-h-svh flex flex-col
   └─ SITE_CONTENT  flex-1 min-h-0
```

#### `BrandLogo` — Klipse 워드마크가 실제로 그리는 것

```
<span  relative inline-flex items-center justify-center flex-none [line-height:0]
       style="width:{width}px; height:{height}px"
       [data-logo-theme="{themeMode}"]  ← themeMode 를 넘겼을 때만>
  ├─ <Image src="/klipse-light.svg"  alt="Klipse">      ← 라이트 UI 자산
  └─ <Image src="/klipse-dark.svg"   alt="" aria-hidden> ← 다크 UI 자산
```

| | 값 |
| --- | --- |
| 두 `<Image>` 공통 클래스 | `absolute left-0 top-0 block w-full h-full object-contain` · `draggable={false}` |
| 전환 방식 | 크로스페이드가 아니라 **동시 스택 + 3속성 토글** — 노출 `opacity-100 visible pointer-events-auto`, 은폐 `opacity-0 invisible pointer-events-none`. transition 선언 **없음**(즉 즉시 전환) |
| `themeMode` **미전달** | 라이트 자산이 기본 노출 + `dark:opacity-0 dark:invisible dark:pointer-events-none`, 다크 자산은 반대 → **`html[data-theme="dark"]` 를 따라 자산이 바뀐다. 라이트 테마에서는 `/klipse-light.svg` 가 보인다** |
| `themeMode="dark"` 전달 | `/klipse-dark.svg` **고정**(전역 테마 무관) |
| 자산 색 | `/klipse-light.svg` = `fill="black"` · `/klipse-dark.svg` = `fill="white"`. 둘 다 `viewBox="0 0 291 85"`, 좌측 결합 마크 사각 영역 72×72 |
| 프레임 크기 출처 | **클래스가 아니라 호출부 인자** — 루트의 `width`/`height` 는 인라인 style 로만 들어간다 |

#### `<form>` 안쪽 — 직계 자식 세로 순서

**6.15** 는 컨트롤 하나하나의 값을 다루고, 여기서는 **그것들이 어떤 순서로 몇 개 놓이는지**를 고정한다. 이 순서를 모르면 화면을 재현할 수 없다.

**`/signup`** — `<form className="w-full grid gap-7">`(row-gap **14px**), 직계 자식 **7개**:

| # | 요소 | 조건 |
| --- | --- | --- |
| ① | **사용자 이름** 단일 박스 `div`(`INPUT_BOX` + `INPUT_BOX_SINGLE` = `rounded-12`) | 상시 |
| ② | **이메일** 단일 박스 `div`(`INPUT_BOX` + `INPUT_BOX_SINGLE`) | 상시 |
| ③ | **스택 캡슐** `div.INPUT_GROUP`(`w-full`) — 안에 비밀번호 박스(`INPUT_BOX_TOP`) → 비밀번호 확인 박스(`INPUT_BOX_BOTTOM`) → **CapsLock 경고 `<p>`** | 상시 (경고만 조건부) |
| ④ | **비밀번호 규칙 힌트** `<p id={passwordRulesHintId}>` | 상시 |
| ⑤ | **동의 블록** `div.LEGAL_AGREEMENTS` (개인정보처리방침 → 서비스 이용약관) | 상시 |
| ⑥ | **오류** `<p>` | `error` 가 빈 문자열이 아닐 때 |
| ⑦ | **제출** `<button type="submit">` | 상시 |

**오류 문단은 동의 블록 *아래*, 제출 버튼 *위*다.** 그리고 **CapsLock 경고는 `<form>` 의 자식이 아니라 `INPUT_GROUP` 의 마지막 자식**이라 폼 gap(14px)을 먹지 않고 캡슐 높이만 늘린다.

#### 검증 순서와 오류 분기

**`/login` 제출 실패** — 우선순위대로: `reason === "network"` → `errorNetwork` · `code === "INVALID_CREDENTIALS"` → `errorInvalidCredentials` · `code === "EMAIL_NOT_VERIFIED"` → `errorEmailNotVerified` · 원문 소문자에 `"invalid login credentials"`/`"invalid credentials"` 포함 → `errorInvalidCredentials` · `"email not confirmed"`/`"email not verified"` 포함 → `errorEmailNotVerified` · 그 외 `result.error?.trim()`, 비면 `errorGeneric`. **`code === "ACCOUNT_DELETED"`(= `DELETED_ACCOUNT_CODES`)는 오류를 지우고 `/recover` 로 push** — 문구가 뜨지 않는다. 제출 전 검증은 `!email || !password` → `errorRequired` 하나뿐이다. `[login:268, :277-309, :354-385]`

**`/signup` · `/aws/signup` 클라이언트 검증** — 순서가 같다:
① `username.trim()`·`email.trim()`·`password` 중 빈 값 → `errorRequired`
② `password !== passwordConfirm` → `errorMismatch`
③ `!agreePrivacy || !agreeTerms` → `signupLegal.errorAgreementsRequired`
④ `password.length < 8` → `errorLength`
⑤ `/(?=.*[a-zA-Z])(?=.*[\d!@#$%^&*])/` 불통과 → `errorComplexity`
**동의 검사가 비밀번호 정책보다 앞**이라 8자 미만이어도 동의를 먼저 요구한다. `[signup:301-328 · aws:344-366]`

**`/reset-password` 검증** — `!normalizedEmail`(trim+소문자) → `errorRequired`. 그 다음 `remainingMs > 0` 이면 **무반응으로 return**(버튼도 이미 disabled). `[reset-password:145-150]`

**`/reset-password/new` 검증** — ① `!password || password.length < 8` → `errorLength` ② 복잡도 → `errorComplexity` ③ 불일치 → `errorMismatch`. **`/signup` 과 순서가 다르다** — 여기서는 불일치가 **마지막**이다. `[new:132-144]`

#### `/login?recovery=true` — 도착 화면에는 아무 안내가 없다

`/aws/signup` 은 `ACCOUNT_DELETED_RECOVERABLE` 을 받으면 `setError("")` 후 `router.replace("/login?recovery=true")` 한다(`aws:388-393`).

#### 놓치기 쉬운 것

- **인증 화면에는 카드 면이 없다.** `CARD` 상수에 background·border·shadow 가 하나도 없다 — 폼은 페이지 바닥 위에 직접 떠 있다. 라이트에서는 입력 박스마저 페이지와 같은 #f1f1f3 이라, 화면에서 실제로 칠해진 면은 **좌측 브랜드 패널과 제출 버튼 둘뿐**이다. "카드"라는 이름에 속아 패널을 그리면 배포와 달라진다.
- **`--gray-000` 을 흰색으로 읽으면 안 된다.** 라이트에서 `--gray-000` = **#000000**, `--gray-1000` = **#fafafa** 로 완전히 뒤집힌다. 따라서 `bg-gray-000 text-gray-1000` 제출 버튼은 다크에서 흰 버튼/검은 글자, **라이트에서 검은 버튼/흰 글자**다.
- **전역 셸과 페이지 바닥의 명암 관계가 테마별로 반대다.** 다크는 둘 다 #171b22 로 같아 이음매가 없지만, 라이트는 뒤쪽 셸 #e3e4e8 이 페이지 #f1f1f3 보다 어둡다.
- **모바일 페이지 패딩이 계열마다 다르다.** `/login`·`/signup`·`/recover`·`/aws/signup` 은 ≤719px 에서 16px, `AuthStatusCard` 를 쓰는 5개 라우트는 그 분기가 없어 **20px** 이다. 한 값으로 스펙하면 5개 화면이 틀린다.
- **`/login`·`/signup` 은 모바일에서 제목·부제를 아예 숨긴다.** "모바일 = 데스크톱에서 브랜드 패널만 뺀 것"이 아니다.
- **자간 강제는 제목뿐이 아니다.** `/login`·`/signup` 의 `SUBTITLE` 과 `AuthStatusCard` 의 `DESCRIPTION` 에도 `letter-spacing: 0` 이 `!` 로 걸려 있다. body-16 의 기본 자간은 **−0.01em** 이므로 강제를 빠뜨리면 8개 화면의 부제 자간이 전부 틀린다. **반대로 `/recover` 의 안내문에는 그 강제가 없어 −0.01em 그대로다** — 유일한 예외다.
- **부제 3종의 색·최대폭이 다르다.** `/login`·`/signup` 은 `…/60%` 에 폭 제한 없음, `AuthStatusCard` 는 **`…/62%` + `max-w-[340px]`**.
- **`/recover` 는 2패널이 아니다.** 브랜드 패널·폼 패널·스크롤 영역이 전부 없고, 워드마크가 모든 폭에서 보이며, 카드 gap 이 어느 폭에서나 8px 이고, 제출 버튼이 `rounded-[999px]` 알약이며, 하단 링크가 body-16 이고(다른 곳은 14), 라이트 필드 오버라이드가 없고, 카드 안에 `<h1>` 이 없으며, i18n 을 쓰지 않는다. **인증 그룹에서 가장 많이 어긋나는 화면이다.**

#### 약관 모달 본문 — 마크다운 요소별 서식

앞 표의 "본문 타이포"·"링크" 행은 **컨테이너 `<div class={LEGAL_MARKDOWN}>` 과 `<a>`** 의 값이다. 그 컨테이너에는 조상 후손 선택자(`[&_h1]:` 형태, 출력 특이도 (0,1,1))로 **14종의 요소 규칙**이 더 걸려 있고, `react-markdown` + `remark-gfm` 이 뱉는 나머지 요소는 규칙이 없다.

색은 전부 `rgb(var(--gray-000-rgb)/N%)` 형태다. `--gray-000-rgb` 는 **다크 `250 250 250` / 라이트 `0 0 0`** 이므로, 아래 표의 `/96%` 는 다크 `rgb(250 250 250 / 96%)` · 라이트 `rgb(0 0 0 / 96%)` 로 읽는다. **카드 면(다크 #313640 / 라이트 #f1f1f3)은 반전하지 않는데 이 글자색은 반전한다.**

#### 같은 메뉴의 배치 산식

메뉴는 `document.body` 로 포털되므로 좌표가 전부 JS 로 계산돼 인라인 style 에 들어간다. `viewportPadding = 8`(px) 하나가 모든 여백을 만든다.

| | 산식 | 결과 |
| --- | --- | --- |
| 세로 (기본) | `top = min(innerHeight − 8 − menuHeight, rect.bottom + 8)` | **트리거 아래 8px**, 단 뷰포트 하단 8px 안쪽으로 밀어 넣는다 |
| 위로 플립 조건 | `menuHeight > (innerHeight − rect.bottom − 8)` **그리고** `(rect.top − 8) > (innerHeight − rect.bottom − 8)` | 아래가 모자라고 **위가 더 넓을 때만** placement=`top` |
| 세로 (플립) | `top = max(8, rect.top − menuHeight − 8)` | 트리거 위 8px |
| 가로 | `left = min(max(8, rect.left), innerWidth − 8 − menuWidth)` | **트리거 좌측 정렬** 후 양옆 8px 클램프 |
| `menuWidth` | `max(menuEl.offsetWidth ?? 0, rect.width)` | 측정 전 프레임에서는 트리거 폭(36px)로 대체 |
| `minWidth` | `rect.width` → 인라인 `minWidth: 36px` | 실질 하한은 `LANG_DROPDOWN` 의 `min-w-[120px]` |
| `width` / `maxWidth` | `max-content` / `calc(100vw − 16px)` | `width` 를 고정한 이유는 shrink-to-fit ↔ `offsetWidth` 재측정이 서로를 키워 **스크롤할 때마다 메뉴가 8px 씩 넓어지던 루프**를 끊기 위해서라고 주석에 적혀 있다 |

**트리거 클릭 시점의 1차 좌표는 위 산식과 다르다** — 메뉴가 아직 측정되지 않아 `top = min(innerHeight − 8, rect.bottom + 8)`(menuHeight 를 빼지 않는다), `left` 클램프도 `menuWidth` 가 아니라 `rect.width` 로 한다. 정확한 값은 직후 layout effect 의 `updateMenuPosition()` + rAF 2회 재측정이 덮는다. 이 1프레임 차이는 `visibility: hidden` 게이트에 가려진다.

좌표는 `resize` 와 **캡처 단계(`capture: true`) `scroll`** 에서 재계산된다 — 조상 스크롤 컨테이너의 스크롤도 잡기 위해서다. `/aws/signup` 트리거는 `position: fixed`(`top-12 right-10`) 라 실제로 움직이지는 않는다.

**테마 — 최종적으로는 OS 설정을 따르고, 인증 화면에는 이를 바꿀 UI 가 없다.**

#### `/aws/signup` 필드 박스 — idle / focus 선언
